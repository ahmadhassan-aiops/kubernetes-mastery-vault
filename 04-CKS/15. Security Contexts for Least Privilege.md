# 15. Security Contexts for Least Privilege

A **securityContext** is a block in the pod or container spec that sets privilege and access controls: which user runs the process, whether it can gain privileges, which Linux capabilities it has, and more.

- Set at the **pod level**, it applies to **all containers** in the pod.
- Set at the **container level**, it applies to that container and **overrides** the pod-level value for the same field.

> The full field reference is in [CKAD topic 15](../02-CKAD/15.%20Security%20Contexts.md). This topic shows **why** it matters, with a before and after from my machine.

## Why It Matters

By default, a container runs as **root (UID 0)**. If an attacker breaks into the application, they are root inside the container, and one container escape away from root on the node.

### UIDs in brief

| ID | Meaning |
|---|---|
| UID 0 | root: full control |
| UID 1000 | Usually the first normal user on a Linux system |
| Other UIDs (2000, 3000, ...) | Any number works; it doesn't need to exist in `/etc/passwd` |
| GID | Same idea for groups |

A non-root user can read most system files but can't modify them, and can't create files in root-owned directories. It can only write where it has ownership or permission.

## Lab on My RHEL Host (Minikube)

### Step 1: A pod with no security context

```yaml
# 1test-unsecure-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: unsecure-pod
spec:
  containers:
  - name: sec-ctx-demo
    image: busybox:1.28
    command: ["sh", "-c", "sleep 1h"]
```

```text
[ahmad@client1 cks]$ kubectl apply -f 1test-unsecure-pod.yaml
pod/unsecure-pod created

[ahmad@client1 cks]$ kubectl get po
NAME           READY   STATUS    RESTARTS   AGE
unsecure-pod   1/1     Running   0          14s

[ahmad@client1 cks]$ kubectl exec -it unsecure-pod -- /bin/sh
/ # whoami
root
```

The prompt is `#`, and `whoami` confirms **root**.

### Step 2: A pod with pod-level and container-level security contexts

```yaml
# test-pod1.yaml
apiVersion: v1
kind: Pod
metadata:
  name: security-context-demo
spec:
  securityContext:          # pod level: applies to all containers
    runAsUser: 1000
    runAsGroup: 3000
  containers:
  - name: sec-ctx-demo
    image: busybox:1.28
    command: ["sh", "-c", "sleep 1h"]
    securityContext:        # container level: overrides runAsUser
      runAsUser: 2000
```

```text
[ahmad@client1 cks]$ kubectl apply -f test-pod1.yaml
pod/security-context-demo created

[ahmad@client1 cks]$ kubectl get po
NAME                    READY   STATUS    RESTARTS   AGE
security-context-demo   1/1     Running   0          3s
unsecure-pod            1/1     Running   0          72s

[ahmad@client1 cks]$ kubectl exec -it security-context-demo -- /bin/sh
/ $ whoami
whoami: unknown uid 2000
```

- The prompt is now `$`: a **non-root** user.
- The container runs as **UID 2000** (the container setting overrides the pod's 1000), with group **3000** from the pod level.
- `unknown uid 2000` only means the busybox image has no `/etc/passwd` entry for 2000. The process still runs with that UID.

Check it fully with `id`, which prints the numeric IDs:

```bash
/ $ id
# expected: uid=2000 gid=3000
```

### Can the user become root again?

**Not from inside the container.** There's no password or `sudo` to switch users, and with `allowPrivilegeEscalation: false` even setuid binaries can't raise privileges.

If one step really needs root (for example, fixing file ownership on a volume), keep it out of the main container: run it in an **init container**, or use `fsGroup` so Kubernetes sets volume permissions for you. Any container that runs as root is itself a risk, so keep it as small and short-lived as possible.

## A Hardened Baseline

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hardened
spec:
  securityContext:
    runAsNonRoot: true            # refuse to start if the image would run as root
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001                # group ownership for mounted volumes
    seccompProfile:
      type: RuntimeDefault        # see topic 14
  containers:
  - name: app
    image: nginxinc/nginx-unprivileged:1.27
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
    volumeMounts:
    - name: tmp
      mountPath: /tmp
  volumes:
  - name: tmp
    emptyDir: {}                  # writable scratch space with a read-only root filesystem
```

| Setting | Protects against |
|---|---|
| `runAsNonRoot` / `runAsUser` | Running as root |
| `allowPrivilegeEscalation: false` | Gaining privileges through setuid binaries |
| `readOnlyRootFilesystem: true` | Attackers writing tools or changing binaries |
| `capabilities.drop: ["ALL"]` | Kernel capabilities the app doesn't need |
| `seccompProfile: RuntimeDefault` | Dangerous system calls |

These settings match the **`restricted` Pod Security Standard**:

```bash
kubectl label namespace prod pod-security.kubernetes.io/enforce=restricted
```

Reference: https://kubernetes.io/docs/tasks/configure-pod-container/security-context/
