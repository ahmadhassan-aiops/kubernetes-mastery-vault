# 04. Securing Ingress with TLS

**Ingress security control** means encrypting the traffic between users and the cluster with **TLS**. In this topic we expose a web server over plain HTTP first, then secure it with a TLS certificate stored in a Kubernetes Secret.

> The Ingress basics (rules, paths, controllers) are in [CKAD topic 26](../02-CKAD/26.%20Ingress%20Networking.md).

## Prerequisites

- A running cluster and kubectl
- An **Ingress controller**. Without one, Ingress objects are accepted but nothing serves them (you'll see this below).
- A TLS certificate and key. In production, get them from a Certificate Authority; for testing, generate a self-signed pair with `openssl`.

### Step 4: Generate a self-signed certificate

```bash
openssl req -x509 -newkey rsa:4096 -sha256 -nodes \
  -keyout tls.key -out tls.crt \
  -subj "/CN=ahmad.com" -days 365
```

> **Watch the line break.** On my first try the command was split so that `subj "/CN=..."` landed on its own line without the leading dash. openssl then prompted interactively for the Distinguished Name, and bash complained `subj: command not found`. Keep `-subj` on the same command (or use `\` continuations as above) and openssl won't prompt.

```text
[ahmad@client1 cks]$ ll
total 12
-rw-r--r--. 1 ahmad ahmad  288 Jul 17 01:49 ingress.yaml
-rw-r--r--. 1 ahmad ahmad 1931 Jul 17 02:12 tls.crt
-rw-------. 1 ahmad ahmad 3268 Jul 17 02:12 tls.key
```

Note that `tls.key` is created with `-rw-------` permissions: only the owner can read the private key.

### Step 5: Store the pair in a TLS Secret

```text
[ahmad@client1 cks]$ kubectl create secret tls sec-ahmad --cert=tls.crt --key=tls.key
secret/sec-ahmad created

[ahmad@client1 cks]$ kubectl get secret
NAME        TYPE                DATA   AGE
sec-ahmad   kubernetes.io/tls   2      6s
```

The `kubernetes.io/tls` type holds exactly two keys: `tls.crt` and `tls.key`.

### Step 6: Add TLS to the Ingress

```yaml
# secure_ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: simple-ingress
spec:
  tls:
  - hosts:
    - ahmad.com
    secretName: sec-ahmad
  rules:
  - host: ahmad.com
    http:
      paths:
      - pathType: Prefix
        path: "/"
        backend:
          service:
            name: caddy-svc
            port:
              number: 80
```

```text
[ahmad@client1 cks]$ kubectl apply -f secure_ingress.yaml
ingress.networking.k8s.io/simple-ingress configured

[ahmad@client1 cks]$ kubectl get ingress
NAME             CLASS    HOSTS       ADDRESS   PORTS     AGE
simple-ingress   <none>   ahmad.com             80, 443   28m
```

Port **443** now appears.

### Step 7: Test, and the missing controller

```text
[ahmad@client1 cks]$ curl --cacert tls.crt https://ahmad.com
curl: (7) Failed to connect to ahmad.com port 443: Connection refused
```

Connection refused: there was **no Ingress controller** yet. Enable the one Minikube ships with:

```text
[ahmad@client1 cks]$ minikube addons enable ingress

[ahmad@client1 cks]$ kubectl get pods -n ingress-nginx
NAME                                        READY   STATUS      RESTARTS   AGE
ingress-nginx-admission-create-p5fwl        0/1     Completed   0          7m25s
ingress-nginx-admission-patch-ds9jm         0/1     Completed   2          7m25s
ingress-nginx-controller-56d7c84fd4-dvv6t   1/1     Running     0          7m25s
```

Try again with verbose output:

```text
[ahmad@client1 cks]$ curl -v --cacert tls.crt https://ahmad.com
*   Trying 192.168.49.2:443...
* Connected to ahmad.com (192.168.49.2) port 443 (#0)
* ALPN, offering h2
* ALPN, offering http/1.1
*  CAfile: tls.crt
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
* TLSv1.3 (IN), TLS handshake, Server hello (2):
* TLSv1.3 (IN), TLS handshake, Encrypted Extensions (8):
* TLSv1.3 (IN), TLS handshake, Certificate (11):
* TLSv1.3 (OUT), TLS alert, unknown CA (560):

```

The TLS handshake now happens on port 443. curl rejects the certificate because it is **self-signed** (no trusted CA vouches for it). For a lab, skip verification:

```bash
curl -k https://ahmad.com
```

You get the Caddy welcome page, served over HTTPS. In production, use a certificate from a real CA (for example via cert-manager and Let's Encrypt) and curl verifies it without `-k`.

## Lab 2: kind with Two Apps and HTTPS Redirect

On kind, the ingress-nginx controller must run on the **control-plane node**, and ports 80 and 443 must be mapped from the host into that node.

### Step 1: A kind cluster with port mappings

```yaml
# kind-ingress.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
  extraPortMappings:
  - containerPort: 80
    hostPort: 80
    protocol: TCP
  - containerPort: 443
    hostPort: 443
    protocol: TCP
```

```bash
kind create cluster --config kind-ingress.yaml
```

### Step 2: Install ingress-nginx

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.9.4/deploy/static/provider/cloud/deploy.yaml
kubectl get pods -n ingress-nginx -o wide   # make sure they land on the control-plane node
```

### Step 3: Certificate and Secret

```bash
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout tls.key -out tls.crt \
  -subj "/CN=ahmad.com/O=ahmad.com"

kubectl create secret tls ahmad-tls --cert=tls.crt --key=tls.key
```

### Step 4: Two apps and their services

`hashicorp/http-echo` returns a fixed text, which makes routing easy to see.

```yaml
# apps.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app1
spec:
  replicas: 1
  selector:
    matchLabels:
      app: app1
  template:
    metadata:
      labels:
        app: app1
    spec:
      containers:
      - name: app1
        image: hashicorp/http-echo
        args: ["-text=Hello from App 1"]
        ports:
        - containerPort: 5678
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app2
spec:
  replicas: 1
  selector:
    matchLabels:
      app: app2
  template:
    metadata:
      labels:
        app: app2
    spec:
      containers:
      - name: app2
        image: hashicorp/http-echo
        args: ["-text=Hello from App 2"]
        ports:
        - containerPort: 5678
---
apiVersion: v1
kind: Service
metadata:
  name: app1-service
spec:
  selector:
    app: app1
  ports:
  - port: 80
    targetPort: 5678
---
apiVersion: v1
kind: Service
metadata:
  name: app2-service
spec:
  selector:
    app: app2
  ports:
  - port: 80
    targetPort: 5678
```

### Step 5: The TLS Ingress with forced HTTPS

```yaml
# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ahmad-ingress
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"   # HTTP requests are redirected to HTTPS
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - ahmad.com
    secretName: ahmad-tls
  rules:
  - host: ahmad.com
    http:
      paths:
      - path: /app1
        pathType: Prefix
        backend:
          service:
            name: app1-service
            port:
              number: 80
      - path: /app2
        pathType: Prefix
        backend:
          service:
            name: app2-service
            port:
              number: 80
```

```bash
kubectl apply -f apps.yaml
kubectl apply -f ingress.yaml
echo "127.0.0.1 ahmad.com" | sudo tee -a /etc/hosts   # kind maps the ports to localhost

curl -k https://ahmad.com/app1   # Hello from App 1
curl -k https://ahmad.com/app2   # Hello from App 2
curl -I http://ahmad.com/app1    # 308 Permanent Redirect to https
```

## Going Further

- **Authentication:** add basic auth or an external auth service with ingress-nginx annotations so only authorized users reach the app.
- **Load balancing:** the Ingress controller spreads traffic across all pods behind each service.
- **Annotations:** rewrites, rate limiting and allow-listing source IPs (`nginx.ingress.kubernetes.io/whitelist-source-range`).

Reference: https://kubernetes.io/docs/concepts/services-networking/ingress/#tls
