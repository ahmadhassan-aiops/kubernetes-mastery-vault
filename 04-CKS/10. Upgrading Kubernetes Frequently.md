# 10. Upgrading Kubernetes Frequently

## What the Objective Means

"Update Kubernetes frequently" means keeping the **whole cluster** current:

- the control plane: kube-apiserver, kube-controller-manager, kube-scheduler, etcd
- the kubelet and kube-proxy on every node
- tools such as kubeadm and kubectl

Outdated clusters carry **known vulnerabilities** that allow unauthorized access, privilege escalation or data leaks; they also run deprecated APIs and miss newer security features.

### The release cycle

- Kubernetes ships a new minor version roughly **every 4 months** (three a year).
- The **three most recent minor versions** receive patches, about **14 months** of support each.
- Upgrade **one minor version at a time** (1.29 → 1.30 → 1.31). Skipping minor versions isn't supported.

### Version skew rules

| Component | Allowed relative to kube-apiserver |
|---|---|
| kube-controller-manager, kube-scheduler | Same or one minor version **older** |
| kubelet, kube-proxy | Up to three minor versions **older**, never newer |
| kubectl | One minor version older or newer |

That's why the **control plane is always upgraded first**.

## Two Common Setups

| Setup | Tool | Upgrade method |
|---|---|---|
| Production clusters | kubeadm | Upgrade in place, node by node |
| Local labs and testing | kind | Delete and recreate the cluster with a newer node image |

## Lab: Upgrading a kind Cluster

### Step 1: Install a newer kind binary

```bash
sudo rm -f /usr/local/bin/kind

curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.23.0/kind-linux-amd64
chmod +x ./kind
sudo mv ./kind /usr/local/bin/kind

kind version
```

### Step 2: Back up, delete and recreate

kind clusters can't be upgraded in place. **Save your manifests first** (deployments, services, secrets and so on).

```bash
kubectl get all,configmaps,secrets -A -o yaml > backup.yaml   # or keep your YAML files in Git

kind delete cluster
kind create cluster --image kindest/node:v1.30.0
```

A multi-node cluster on the new version:

```yaml
# cluster-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: worker
- role: worker
- role: worker
```

```bash
kind create cluster --config cluster-config.yaml --image kindest/node:v1.30.0
kubectl get nodes        # all nodes report v1.30.0
```

Each kind release lists the node images it supports in its release notes.

## Production: Upgrading a kubeadm Cluster

You don't do this on kind, but the CKS (and CKA) expects you to know the procedure. Example: 1.29 → 1.30 on Ubuntu.

### 1. Back up etcd

```bash
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-$(date +%F).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
```

(More on etcd in [CKA topic 02](../03-CKA/02.%20etcd%20in%20Kubernetes.md).)

### 2. Upgrade kubeadm on the first control-plane node

Point the package repository at the new minor version (`pkgs.k8s.io/core:/stable:/v1.30/deb/`), then:

```bash
sudo apt-mark unhold kubeadm
sudo apt-get update && sudo apt-get install -y kubeadm='1.30.x-*'
sudo apt-mark hold kubeadm
kubeadm version
```

### 3. Plan and apply

```bash
sudo kubeadm upgrade plan              # shows available versions and what will change
sudo kubeadm upgrade apply v1.30.x     # upgrades the control-plane components
```

On additional control-plane nodes, run `sudo kubeadm upgrade node` instead.

### 4. Upgrade the kubelet and kubectl on the control plane

```bash
kubectl drain <control-plane-node> --ignore-daemonsets

sudo apt-mark unhold kubelet kubectl
sudo apt-get install -y kubelet='1.30.x-*' kubectl='1.30.x-*'
sudo apt-mark hold kubelet kubectl
sudo systemctl daemon-reload && sudo systemctl restart kubelet

kubectl uncordon <control-plane-node>
```

### 5. Upgrade each worker, one at a time

```bash
# on the worker: upgrade kubeadm as in step 2, then
sudo kubeadm upgrade node

# from a machine with kubectl
kubectl drain <worker> --ignore-daemonsets --delete-emptydir-data

# on the worker: upgrade kubelet and kubectl as in step 4, restart the kubelet

kubectl uncordon <worker>
```

### 6. Verify

```bash
kubectl get nodes    # every node shows v1.30.x and Ready
```

## Best Practices

- Follow the Kubernetes security announcements and patch releases.
- Rehearse upgrades in a staging cluster first.
- Check for **deprecated APIs** in your manifests before each minor upgrade.
- Upgrade workers one at a time with **drain** so workloads keep running.
