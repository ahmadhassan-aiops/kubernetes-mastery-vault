# 13. Kernel Hardening with AppArmor

## Background: User Space and Kernel Space

Every Linux host has a **kernel space** and a **user space**. Applications (and containers) run in user space and ask the kernel to do things for them through **system calls**: open, read, write, close and so on.

Containers share the host's kernel, so restricting what they can ask the kernel to do is a powerful defense. Two tools do this:

| Tool | Restricts | Topic |
|---|---|---|
| **AppArmor** | Which **files, capabilities and network access** a program may use | this topic |
| **seccomp** | Which **system calls** a program may make | [14](14.%20Kernel%20Hardening%20with%20seccomp.md) |

## What Is AppArmor?

**AppArmor** is a Linux security module. It confines programs with **profiles**: sets of rules loaded into the kernel that describe what a program may access.

A profile loads in one of two modes:

| Mode | Behaviour |
|---|---|
| **Enforce** | Blocks anything the profile doesn't allow, and logs it |
| **Complain** | Allows everything but logs violations; useful while building a profile |

Profiles live in **`/etc/apparmor.d/`**.

## The Workflow

1. Make sure AppArmor is installed and enabled on **every node**
2. Write the profile
3. Load it on **every node** where the pod might run
4. Reference it in the pod
5. Verify

## Lab

### Step 1: Check AppArmor on the node

AppArmor comes by default with Ubuntu.

```bash
sudo systemctl status apparmor
cat /sys/module/apparmor/parameters/enabled    # Y
sudo aa-status                                 # loaded profiles and their modes
```

### Step 2: Write a profile that denies all writes

```bash
sudo vim /etc/apparmor.d/k8s-apparmor-example-deny-write
```

```text
#include <tunables/global>

profile k8s-apparmor-example-deny-write flags=(attach_disconnected) {
  #include <abstractions/base>

  file,

  # Deny all file writes.
  deny /** w,
}
```

- `file,` allows general file access.
- `deny /** w,` then denies **writes** anywhere in the filesystem.

### Step 3: Load it

```bash
sudo apparmor_parser /etc/apparmor.d/k8s-apparmor-example-deny-write
sudo aa-status | grep k8s-apparmor-example-deny-write   # confirm it's loaded (enforce mode)
```

Repeat on every node. (In real clusters, a DaemonSet or a configuration tool distributes and loads profiles.)

### Step 4: First, a pod without the profile

```yaml
# pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: hello-apparmor
spec:
  containers:
  - name: hello
    image: busybox:1.28
    command: ["sh", "-c", "echo 'Hello AppArmor!' && sleep 1h"]
```

```bash
kubectl apply -f pod.yaml
kubectl exec -it hello-apparmor -- sh
/ # echo '12345' > test.txt
/ # ls
test.txt  ...                    # the write works
/ # exit
```

### Step 5: Now with the profile

From Kubernetes **v1.30**, the profile is set in the `securityContext`:

```yaml
# pod2.yaml
apiVersion: v1
kind: Pod
metadata:
  name: hello-apparmor
spec:
  containers:
  - name: hello
    image: busybox:1.28
    command: ["sh", "-c", "echo 'Hello AppArmor!' && sleep 1h"]
    securityContext:
      appArmorProfile:
        type: Localhost
        localhostProfile: k8s-apparmor-example-deny-write
```

On older clusters, use the (now deprecated) annotation instead, where `hello` is the container name:

```yaml
metadata:
  annotations:
    container.apparmor.security.beta.kubernetes.io/hello: localhost/k8s-apparmor-example-deny-write
```

```bash
kubectl delete pod hello-apparmor
kubectl apply -f pod2.yaml
kubectl describe pod hello-apparmor

kubectl exec -it hello-apparmor -- sh
/ # touch test
touch: test: Permission denied
/ # echo '123445' > text2.txt
sh: can't create text2.txt: Permission denied
```

Both writes are blocked by the kernel, even though the container runs as root.

You can also confirm the profile from inside the container:

```bash
kubectl exec hello-apparmor -- cat /proc/1/attr/current
# k8s-apparmor-example-deny-write (enforce)
```

### Profile types

| `type` | Meaning |
|---|---|
| `RuntimeDefault` | The container runtime's default profile (a good baseline) |
| `Localhost` | A profile loaded on the node, named in `localhostProfile` |
| `Unconfined` | No AppArmor confinement (avoid) |

> If a pod references a profile that **isn't loaded** on its node, the container won't start. That's why the profile must be on every node.

### Step 6: Clean up

Unload the profile:

```bash
sudo apparmor_parser -R /etc/apparmor.d/k8s-apparmor-example-deny-write
sudo aa-status
```
