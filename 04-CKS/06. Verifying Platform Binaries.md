# 06. Verifying Platform Binaries

**Verifying platform binaries** means making sure every Kubernetes component you run (kubectl, kubelet, kube-apiserver, etcd and so on) is the **authentic, unmodified** build from the official release.

It protects against:

- attackers replacing binaries with compromised versions
- accidentally using wrong or modified versions
- inconsistency across the nodes of a cluster

## Two Ways to Verify

| Method | How it works | Proves |
|---|---|---|
| **Checksums** | Hash the downloaded file and compare it with the hash published by the project | The file wasn't corrupted or changed after the hash was published |
| **Signatures** | Verify a cryptographic signature with the project's public key (GPG, or Sigstore `cosign` for current Kubernetes releases) | The file was produced and signed by the project |

## Lab: Verify a Kubernetes Client Binary

### Step 1: Find your version

```bash
kubectl version
```

In my lab the client was **v1.32.3**.

### Step 2: Download the matching release

Releases are listed at https://github.com/kubernetes/kubernetes/releases. For Linux on 64-bit Intel/AMD, pick the `linux-amd64` archive:

```bash
curl -LO https://dl.k8s.io/v1.32.3/kubernetes-client-linux-amd64.tar.gz
```

### Step 3: Calculate the hash

```bash
sha512sum kubernetes-client-linux-amd64.tar.gz
```

### Step 4: Compare it with the published hash

Open the release page (or the `CHANGELOG` for that minor version), press **Ctrl+F** and paste your hash.

- **Match found:** the binary is authentic.
- **No match:** you may have downloaded a tampered binary, or hashed the wrong file. Don't use it.

### Doing it without the browser

The release server publishes a hash file next to each binary, so the comparison can be scripted:

```bash
curl -LO "https://dl.k8s.io/release/v1.32.3/bin/linux/amd64/kubectl"
curl -LO "https://dl.k8s.io/release/v1.32.3/bin/linux/amd64/kubectl.sha256"

echo "$(cat kubectl.sha256)  kubectl" | sha256sum --check
# kubectl: OK
```

`OK` means the hashes match; `FAILED` means they don't.

## Verifying Binaries Already on a Node

On a control-plane node, the components run from container images, but `kubelet` and `kubectl` are files on disk. Compare their hashes with the release:

```bash
which kubelet          # e.g. /usr/bin/kubelet
sha512sum /usr/bin/kubelet
kubelet --version      # find the matching release, then compare
```

## Signature Verification

Current Kubernetes release artifacts and images are signed with **Sigstore**:

```bash
cosign verify-blob kubectl \
  --signature kubectl.sig \
  --certificate kubectl.cert \
  --certificate-identity krel-staging@k8s-releng-prod.iam.gserviceaccount.com \
  --certificate-oidc-issuer https://accounts.google.com
```

Search for "verify signed artifacts kubernetes" to find the official page: https://kubernetes.io/docs/tasks/administer-cluster/verify-signed-artifacts/

## Good Practice

- Download only from official sources (`dl.k8s.io`, the project's GitHub releases).
- Build hash or signature checks into your provisioning scripts and CI pipelines.
- Watch the Kubernetes security announcements for compromised or vulnerable releases.
