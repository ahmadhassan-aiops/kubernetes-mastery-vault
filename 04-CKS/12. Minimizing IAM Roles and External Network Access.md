# 12. Minimizing IAM Roles and External Network Access

Two System Hardening objectives that live **outside** Kubernetes itself: the cloud account the cluster runs in, and the network around it.

---

## Part 1: Minimizing IAM Roles (AWS)

Cloud IAM permissions are often the most powerful credentials around a cluster. A node role that can read every S3 bucket turns one compromised pod into a data breach.

### Step by step

1. **Find unused roles.** In the IAM console (or `aws iam list-roles` plus "last used" data), look for roles that haven't been used for 30 or 90 days, or aren't attached to any user, group or instance. Delete them.
2. **Review the policies on roles still in use.** Grant only the permissions each one really needs. **IAM Access Analyzer** shows which permissions have never been used.
3. **Use AWS managed policies** for common cases, which reduces the risk of hand-written policies granting too much by accident.
4. **Write granular policies** when managed ones don't fit: split permissions into small policies so each role gets exactly what it requires.
5. **Add conditions** to restrict access by source IP, time of day, specific resources or MFA.
6. **Use service-specific roles** instead of broad permissions: for example, a role that can only write to one backup bucket for a backup application.
7. **Manage roles as code** with Terraform or CloudFormation, so changes are reviewed and drift is detected.
8. **Review regularly** and remove what's no longer needed.

### Kubernetes-specific points

- **Don't let pods use the node's role.** Give each workload its own role through **IRSA** (IAM Roles for Service Accounts) or **EKS Pod Identity**, linked to a Kubernetes ServiceAccount.
- **Block the instance metadata service** (`169.254.169.254`) from pods with a Network Policy ([topic 02](02.%20Network%20Policies%20and%20Protecting%20Node%20Metadata.md)), and require IMDSv2 with a hop limit of 1.
- **Monitor IAM activity with CloudTrail** and alert on unusual calls.

## Part 2: Minimizing External Network Access

### 1. Use a firewall, deny by default

Allow only authorized traffic by source, destination, port and protocol, and block everything else.

On a node, the ports Kubernetes needs:

| Node | Port(s) | Purpose |
|---|---|---|
| Control plane | 6443 | Kubernetes API |
| Control plane | 2379-2380 | etcd (from control-plane nodes only) |
| Control plane | 10250, 10257, 10259 | kubelet, controller-manager, scheduler |
| Workers | 10250 | kubelet |
| Workers | 30000-32767 | NodePort services (only if you use them) |

Example with UFW on Ubuntu:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 10.0.0.0/16 to any port 6443 proto tcp   # API only from the VPC
sudo ufw allow from 10.0.1.5 to any port 22 proto tcp        # SSH only from the jump host
sudo ufw enable
sudo ufw status numbered
```

On RHEL use `firewalld` (`firewall-cmd`), and in the cloud use **security groups** and **network ACLs**.

### 2. Secure remote access

- Disable unused remote protocols such as Telnet and FTP.
- Use SSH with keys, not passwords ([topic 11](11.%20Minimizing%20the%20Host%20OS%20Footprint.md)); add MFA where possible.
- Allow administration only from specific IPs or through a bastion or VPN.
- Prefer a **private API endpoint** for managed clusters.

### 3. Harden network devices

- Keep router and switch firmware updated.
- Turn off unused features.
- Change all default credentials.

### 4. Segment the network

Put control-plane nodes, workers and databases in separate subnets, so a breach in one segment doesn't open the others. Inside the cluster, Network Policies do the same job between pods.

### 5. Control egress

Restrict what pods can reach outside the cluster: default-deny egress Network Policies, an egress gateway, or a proxy with an allow-list.

### 6. Monitor

- Collect network flow logs (for example VPC Flow Logs) and review them.
- Use IDS/IPS to detect and block malicious traffic.
- Run regular vulnerability scans and train users to spot phishing.
