# 05. Minimizing GUI Access with the Kubernetes Dashboard

The **Kubernetes Dashboard** is a web UI for viewing and managing cluster resources. It's convenient, but an exposed or over-privileged dashboard is a classic way clusters get compromised. The CKS objective is to **minimize use of, and access to, GUI elements**:

- Prefer `kubectl`; run the dashboard only when it's needed.
- **Never expose it publicly.** Reach it through `kubectl proxy` or `kubectl port-forward`, which require valid kubeconfig credentials.
- Log in with a **token** for a dedicated ServiceAccount, never with anonymous or skip-login access.
- Give that ServiceAccount the **least privilege** it needs.

## Lab 1: Minikube Addons on My RHEL Host

### Step 1: Enable metrics-server and the dashboard

`minikube addons list` showed both disabled at first.

```text
[ahmad@client1 ~]$ minikube addons enable metrics-server
* metrics-server is an addon maintained by Kubernetes. For any concerns contact minikube on GitHub.
  - Using image registry.k8s.io/metrics-server/metrics-server:v0.7.2
* The 'metrics-server' addon is enabled

[ahmad@client1 ~]$ minikube addons enable dashboard
* dashboard is an addon maintained by Kubernetes. For any concerns contact minikube on GitHub.
  - Using image docker.io/kubernetesui/dashboard:v2.7.0
  - Using image docker.io/kubernetesui/metrics-scraper:v1.0.8
* The 'dashboard' addon is enabled

[ahmad@client1 ~]$ kubectl get pods -n kubernetes-dashboard
NAME                                         READY   STATUS    RESTARTS   AGE
dashboard-metrics-scraper-5d59dccf9b-cdsj9   1/1     Running   0          13m
kubernetes-dashboard-7779f9b69b-l7j9v        1/1     Running   0          13m
```

Some dashboard features (CPU and memory graphs) need metrics-server, which is why it's enabled first.

On a non-Minikube cluster, install the same version with:

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/dashboard/v2.7.0/aio/deploy/recommended.yaml
```

### Step 2: Create a dedicated login account

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: ServiceAccount
metadata:
  name: admin-user
  namespace: kubernetes-dashboard
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: admin-user
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
- kind: ServiceAccount
  name: admin-user
  namespace: kubernetes-dashboard
EOF
```

> `cluster-admin` is fine for a personal lab. For anyone else, bind a narrower role, such as the built-in `view` ClusterRole, or a Role limited to one namespace (see [topic 08](08.%20RBAC%20with%20User%20Certificates.md)).

### Step 3: Access it through the API server proxy

```bash
kubectl proxy
```

Open:

```text
http://localhost:8001/api/v1/namespaces/kubernetes-dashboard/services/http:kubernetes-dashboard:/proxy/
```

`kubectl proxy` listens only on `localhost` and uses your kubeconfig credentials, so the dashboard is never published on the network.

### Step 4: Log in with a short-lived token

```bash
kubectl -n kubernetes-dashboard create token admin-user
```

Paste the token on the login page. `create token` issues a **time-limited** token (one hour by default) instead of a long-lived secret.

**What this achieves:** only this dedicated account can use the dashboard, access goes through an authenticated proxy, and tokens expire on their own.

## Lab 2: Dashboard v7 with Helm (kind)

Newer dashboard releases are installed with Helm.

```bash
# install Helm
curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
helm version

# add the repo and install the dashboard
helm repo add kubernetes-dashboard https://kubernetes.github.io/dashboard/
helm upgrade --install kubernetes-dashboard kubernetes-dashboard/kubernetes-dashboard \
  --create-namespace --namespace kubernetes-dashboard
```

The Helm chart puts a **Kong proxy** in front of the dashboard. Forward it to your machine only:

```bash
kubectl port-forward -n kubernetes-dashboard svc/kubernetes-dashboard-kong-proxy 8443:443
```

Open `https://localhost:8443`, then create the `admin-user` account and token exactly as in Lab 1 steps 2 and 4.

### What not to do

```bash
# exposes the dashboard to every machine that can reach this host
kubectl port-forward -n kubernetes-dashboard svc/kubernetes-dashboard-kong-proxy 8443:443 --address 0.0.0.0
```

`--address 0.0.0.0` makes the dashboard reachable from the whole network. Avoid it. If remote access is truly needed, put it behind an **Ingress with TLS and authentication** (see [topic 04](04.%20Securing%20Ingress%20with%20TLS.md)), and restrict source IPs:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: dashboard-ingress
  namespace: kubernetes-dashboard
  annotations:
    nginx.ingress.kubernetes.io/backend-protocol: "HTTPS"
    nginx.ingress.kubernetes.io/whitelist-source-range: "10.0.0.0/8"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - dashboard.example.com
    secretName: dashboard-tls
  rules:
  - host: dashboard.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: kubernetes-dashboard-kong-proxy
            port:
              number: 443
```

## Checklist

- [ ] Dashboard installed only where it's needed
- [ ] Accessed via `kubectl proxy` or `port-forward` on localhost
- [ ] Token login with a dedicated ServiceAccount
- [ ] Least-privilege role for that account
- [ ] No `--address 0.0.0.0`, no NodePort or LoadBalancer exposure
