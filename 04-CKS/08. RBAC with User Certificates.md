# 08. RBAC with User Certificates

**Role-Based Access Control (RBAC)** grants users and service accounts the **least privilege** they need, which limits the damage from stolen credentials or insider mistakes.

> RBAC for service accounts, with `kubectl auth can-i`, is covered in [CKAD topic 16](../02-CKAD/16.%20Service%20Accounts%20and%20RBAC.md). Here we create a **real user** with a client certificate and give it read-only access.

## The Four RBAC Objects

| Object | Scope | Purpose |
|---|---|---|
| **Role** | One namespace | A set of permissions (verbs on resources) |
| **ClusterRole** | Cluster-wide | Permissions across all namespaces, or on cluster-scoped resources such as nodes |
| **RoleBinding** | One namespace | Gives a Role (or ClusterRole) to users, groups or service accounts in that namespace |
| **ClusterRoleBinding** | Cluster-wide | Gives a ClusterRole everywhere |

## Scenario

> I need a person who can **see pods only**, nothing else, so they can tell me when a pod is down, pending or failing.

Lab: a kind cluster (`kind-kind`), working from `/home/kubernetes/rbac`.

## Step 1: The Role

```yaml
# rbac-role.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]          # "" is the core API group (pods, services, ...)
  resources: ["pods"]
  verbs: ["get", "list"]
```

## Step 2: The RoleBinding

```yaml
# rbac-binding.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: default
subjects:
- kind: User
  name: ahmad              # must match the certificate's CN
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

```bash
kubectl apply -f rbac-role.yaml -f rbac-binding.yaml
```

Kubernetes has **no User objects**. A "user" is simply the identity in a trusted client certificate: the **CN** is the username and any **O** fields are groups.

## Step 3: Create the User's Key and Certificate Request

```bash
openssl genrsa -out ahmad.key 2048
openssl req -new -key ahmad.key -out ahmad.csr -subj "/CN=ahmad"
```

## Step 4: Sign It with the Cluster CA

The cluster CA lives on the control-plane node in `/etc/kubernetes/pki`. On kind, that node is a Docker container:

```bash
docker cp ahmad.csr kind-control-plane:/etc/kubernetes/pki/ahmad.csr
docker exec -it kind-control-plane bash

# inside the node
cd /etc/kubernetes/pki
openssl x509 -req -in ahmad.csr \
  -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out ahmad.crt -days 365
exit
```

Copy the signed certificate back next to the key:

```bash
docker cp kind-control-plane:/etc/kubernetes/pki/ahmad.crt /home/kubernetes/rbac/ahmad.crt
```

> **Without node access**, use the Kubernetes CSR API instead: create a `CertificateSigningRequest` with `signerName: kubernetes.io/kube-apiserver-client`, approve it with `kubectl certificate approve`, then read the certificate from its status.

## Step 5: Add the User to kubeconfig

```bash
kubectl config set-credentials ahmad \
  --client-certificate=ahmad.crt \
  --client-key=ahmad.key \
  --embed-certs=true
```

`--embed-certs=true` copies the certificate data into kubeconfig, so it keeps working if the files move.

## Step 6: Create a Context and Test

```bash
kubectl config get-clusters          # kind-kind

kubectl config set-context ahmad-context \
  --cluster=kind-kind \
  --user=ahmad

kubectl config get-contexts
kubectl config use-context ahmad-context
```

| Command | Result as `ahmad` |
|---|---|
| `kubectl get pods` | **Works** |
| `kubectl get nodes` | **Forbidden**: nodes aren't in the Role |
| `kubectl delete pod <name>` | **Forbidden**: no `delete` verb |
| `kubectl get pods -n kube-system` | **Forbidden**: the Role is only in `default` |

Switch back to the admin context:

```bash
kubectl config use-context kind-kind
kubectl get nodes      # works again: the default kind user has full privileges
```

You can also test without switching contexts:

```bash
kubectl auth can-i list pods --as ahmad          # yes
kubectl auth can-i list nodes --as ahmad         # no
```

## RBAC Best Practices

- **Least privilege:** grant only the verbs and resources needed; avoid `cluster-admin` except for real administrators.
- **Prefer Roles over ClusterRoles**, and use namespaces to isolate teams.
- **Avoid wildcards** (`*`) in verbs and resources.
- **Watch dangerous permissions:** `create pods`, `get secrets`, `escalate`, `bind` and `impersonate` can all lead to privilege escalation.
- **Review regularly:** remove unused bindings and accounts (`kubectl get rolebindings,clusterrolebindings -A`).
- **Certificates can't be revoked** in Kubernetes: keep their lifetime short, and remove the RoleBinding to cut off a user.
