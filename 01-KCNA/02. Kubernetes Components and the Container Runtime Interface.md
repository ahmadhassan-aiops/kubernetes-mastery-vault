# 02. Kubernetes Components and the Container Runtime Interface

Each component is easier to remember with a real-world analogy.

## Control Plane and Node Components

| Component | What it does | Analogy |
|---|---|---|
| **API Server** | Every request (start an app, scale up, check status) goes here first. It validates the request and stores the desired state in etcd. | The **front desk** of an office: fill in the form, and once approved, the request moves on. |
| **etcd** | The cluster's built-in key-value store and single **source of truth**. The API Server writes the desired state here, and every other component watches it for changes. | The **master ledger** everyone in the office checks to see what should be happening. |
| **kubelet** | Runs on every worker node. It checks (through the API Server) which pods should run on its node, tells the container runtime to start or stop them, and reports the actual state back. | The **building manager** who makes sure every room has the right people and equipment. |
| **Container runtime** | Actually starts and stops containers (containerd, CRI-O, Docker). It pulls the image and sets up networking and storage. | The **kitchen**: the kubelet is the waiter taking the order, the runtime cooks the dish. |
| **Controllers** | Background watchdogs that compare the **desired** state with the **actual** state and fix any difference. Examples: the Deployment controller and the Node controller. | A **floor manager** who calls HR when a team is understaffed. |
| **Scheduler** | Picks the best node for each new pod based on CPU, memory, labels and taints, then tells the API Server where to place it. | An **air traffic controller** assigning flights to free runways. |

## Container Runtime Interface (CRI)

The CRI is a standard **plug-and-play API** that lets Kubernetes talk to any container runtime without custom code for each one.

- Like a **universal wall socket**: any appliance with the right plug just works.
- The kubelet uses the CRI to plug in runtimes such as **containerd** or **CRI-O**.
- You can swap the container runtime without changing Kubernetes itself.

## Open Container Initiative (OCI)

The OCI is an industry standards body under the Linux Foundation that defines how container images and runtimes behave. It publishes two specs:

1. **Image Specification:** how container images are structured.
2. **Runtime Specification:** how to run those images.

Because Docker, containerd, CRI-O and others all follow the OCI specs, you can build an image with one tool and run it with another.

## dockershim

- Early Kubernetes talked to Docker through a built-in adapter called **dockershim**, which translated CRI calls into Docker API calls (a language interpreter between "CRI" and "Docker").
- Docker's daemon bundles an image builder, distribution and a runtime, so this extra layer added complexity.
- **Since Kubernetes v1.24, dockershim has been removed.** Docker-built images still run fine on CRI-compliant runtimes such as containerd, with a simpler and lighter stack.
