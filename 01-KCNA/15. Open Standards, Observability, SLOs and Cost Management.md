# 15. Open Standards, Observability, SLOs and Cost Management

## Open Standards

Open standards are **publicly available, community-driven specifications and APIs** that make cloud-native tools interoperable, portable and vendor-neutral.

Kubernetes is built on open standards such as:

| Standard | Lets Kubernetes work with |
|---|---|
| **CRI** (Container Runtime Interface) | Any runtime: containerd, CRI-O |
| **CSI** (Container Storage Interface) | Any storage solution |
| **CNI** (Container Network Interface) | Any network plugin: Calico, Flannel, Cilium |
| **OCI** (Open Container Initiative) | Standard image and runtime formats |

Benefits: **no vendor lock-in**, easy integration of third-party tools, and portable apps that run the same on any compliant platform.

## Observability Fundamentals

Observability is the ability to understand what's happening **inside** your system from the data it produces. It rests on three pillars:

| Pillar | What it is | Helps with | Common tools |
|---|---|---|---|
| **Logs** | Detailed records of events (container errors, pod restarts) | Debugging specific issues | ELK, Loki |
| **Metrics** | Numbers over time (CPU, memory, request latency) | Monitoring and alerting | Prometheus |
| **Traces** | The path of one request across many services (frontend to backend) | Finding bottlenecks | Jaeger, OpenTelemetry |

Together they help teams detect problems early, find root causes and keep the system healthy.

## SLI, SLO and SLA

These site reliability engineering (SRE) terms define and measure service reliability:

| Term | Meaning | Example |
|---|---|---|
| **SLI** (Service Level Indicator) | A measurable metric of how the system performs | Request success rate, latency, uptime |
| **SLO** (Service Level Objective) | The **target** for an SLI | "99.9% of requests succeed over 30 days" |
| **SLA** (Service Level Agreement) | A formal agreement with customers, with **penalties** if the SLO is missed | "If uptime drops below 99.5%, we refund 10%" |

In Kubernetes, SLIs are often collected with **Prometheus**, and SLOs are watched with alerting rules so reliability goals are met proactively.

## Cost Management

Cost management means **tracking, controlling and optimizing** resource usage to cut unnecessary spending. Because Kubernetes schedules workloads dynamically, it's easy to over-provision CPU, memory or storage and pay for idle resources.

Good practices:

- Set **resource requests and limits** to avoid waste.
- Use **autoscaling** to match demand.
- Monitor usage by namespace, workload or team with **Prometheus + Grafana, Kubecost** or cloud billing tools.
- **Right-size** workloads and use **spot instances** where suitable.
