# 09. Authentication and Authorization

## Security in Kubernetes

Securing a cluster is like locking your house:

- **Who can enter?** → Authentication
- **What are they allowed to do?** → Authorization
- **Is anyone recording what happens?** → Auditing
- **Are conversations private?** → Encryption and TLS

At the centre of it all is the **Kubernetes API Server**, the main gate to the cluster. Everything (kubectl, controllers, users, apps) talks to it, so **protecting the API Server means protecting the cluster.** Think of it as the receptionist in a secure office who checks who you are, whether you're allowed, and logs every action.

Further reading: [Kubernetes API authentication using TLS certificates](https://dreamlab.net/en/blog/post/kubernetes-api-authentication-using-tls-certificates-1/)

## Pillar 1: Authentication ("Who are you?")

Authentication proves your identity; it is the login step.

| Type | Example | Used by |
|---|---|---|
| Certificate-based | X.509 client certificate | Admins, tools |
| Token-based | Bearer token | ServiceAccounts |
| Username/password | Basic auth (deprecated) | Testing only |
| Cloud IAM | AWS, GCP, Azure IAM | Cloud providers |
| External | LDAP, OIDC, Dex | Enterprises |

**Example:** when you run `kubectl get pods`, the API Server first checks whether you have a valid token or certificate. If yes, it moves on to authorization.

## Pillar 2: Authorization ("What can you do?")

Once Kubernetes knows who you are, authorization decides what you may do: create pods, delete services, read secrets, and so on.

### 1. RBAC (Role-Based Access Control): most common

RBAC grants permissions through **Roles** (what actions are allowed) bound to **subjects** (users, groups or service accounts).

```yaml
# Role: pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
```

```yaml
# RoleBinding subject
subjects:
  - kind: User
    name: alice
```

Now `alice` can read pods but cannot delete or edit them. RBAC is the default in most clusters, gives fine-grained control, and works for users and service accounts.

**Analogy:** an access card that opens only the kitchen and the lounge.

### 2. ABAC (Attribute-Based Access Control): legacy

Rules are written in a JSON file based on attributes such as user, resource, verb and namespace:

```json
{
  "user": "bob",
  "resource": "pods",
  "verb": "delete",
  "namespace": "dev"
}
```

This lets `bob` delete pods only in the `dev` namespace. ABAC is hard to manage, has no kubectl tooling, and **every change needs an API Server restart**, so it is rarely used today.

**Analogy:** rules pinned to the wall on paper; every change means rewriting the paper and rebooting the office.

### 3. Webhook authorization: fully custom

Kubernetes sends an HTTP request to **your own authorization service**, which replies yes or no. Use it for policies RBAC can't express, for example:

- allow deleting pods only after 6 PM
- allow access only if the team lead approved the request
- decide access based on an HR system

**Analogy:** calling your manager before every action.

### 4. Node authorization: for kubelets

This mode applies only to **nodes**. It limits each kubelet to reading its own pod specs, the secrets mounted into its pods, and the pods scheduled to it, so Node A can't read Node B's data. It is enabled by default in secure clusters.

**Analogy:** each janitor has a key to their assigned floor only.

### Summary

| Type | What it does | Applies to | Common use |
|---|---|---|---|
| RBAC | Role and permission based | Users, service accounts | Modern clusters |
| ABAC | Attribute rules in a JSON file | Users | Legacy only |
| Webhook | Asks an external system | Users, groups, service accounts | Custom rules |
| Node | Restricts kubelets | Nodes | Always on |

### Authentication vs Authorization

| | Authentication | Authorization |
|---|---|---|
| Question | Who are you? | What can you do? |
| Result | An identity (user or service) | Allowed actions |
| Examples | Certificates, tokens | RBAC, webhooks |
| Managed by | API Server and kubeconfig | RBAC rules and bindings |

**Analogy:** in a game arcade, authentication is the card you scan to get in; authorization is the points on the card that decide which games you can play.

## ClusterRole

A **ClusterRole** is like a Role, but it applies **across the whole cluster** instead of one namespace. Use it for:

- **non-namespaced resources** such as nodes, persistent volumes or cluster-wide settings
- **global permissions** that should apply in every namespace

Grant a ClusterRole with a **ClusterRoleBinding**.
