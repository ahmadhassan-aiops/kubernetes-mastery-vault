# 13. Scaling and Autoscaling

## What Is Scaling?

Scaling means increasing or decreasing computing resources:

- **More or fewer pods** to handle load
- **More or less CPU/memory per pod** for performance

Kubernetes supports **manual and automatic** scaling, in **both directions** (up and down).

| Type | What changes |
|---|---|
| **Horizontal scaling** | Add or remove pod replicas to spread the load |
| **Vertical scaling** | Give an existing pod more or less CPU/memory |
| **Autoscaling** | The system reacts to usage automatically |

## 1. HPA: Horizontal Pod Autoscaler

- **What:** changes the **number of replicas** based on CPU, memory or custom metrics.
- **How:** watches metrics and adjusts the replica count of a Deployment or StatefulSet.
- **Use case:** changing web traffic. More users means more pods.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

## 2. VPA: Vertical Pod Autoscaler

**What:** suggests or automatically changes a pod's CPU/memory **requests and limits**.

**Main parts:**

| Part | Role |
|---|---|
| **Recommender** | Watches usage and suggests the best CPU/memory values |
| **Updater** | Deletes and recreates pods to apply the new values |
| **Admission Controller** | Applies the recommended values when a pod is created |

**Modes:**

- `"Off"`: only collects recommendations (safe to try)
- `"Initial"`: applies recommendations only when a pod starts
- `"Auto"`: actively recreates pods to adjust resources

### When to skip the Updater

- **Stateful or long-running pods** (such as databases) that shouldn't be restarted often
- **Mission-critical production** where sudden pod termination is risky
- When you want to **review recommendations manually** before applying them

In these cases keep the Recommender and Admission Controller, and let the team apply updates by hand.

## HPA vs VPA

| Feature | HPA | VPA |
|---|---|---|
| Scales | Number of replicas | CPU/memory per pod |
| Reacts to | CPU/memory usage, custom metrics | Historical usage |
| Replaces pods? | No | Yes, if the Updater is on |
| Works well with | Stateless services | Light to moderate load services |
| Use together? | Yes, with care to avoid conflicts | Yes |

**Analogy:** HPA hires more workers when the shop is busy; VPA gives each worker a bigger toolset. Sometimes you don't interrupt a busy worker to upgrade their tools, which is when you skip the VPA Updater.

## 3. Cluster Autoscaler

The Cluster Autoscaler changes the **number of nodes**:

- **Scale out:** when pods can't be scheduled for lack of resources, it adds nodes.
- **Scale in:** when nodes are underused and their pods can move safely, it removes nodes to save cost.

It works together with HPA and VPA so that both pods and nodes scale dynamically, and is common in cloud environments (AWS, GCP, Azure) where nodes can be added or removed on demand.
