# 12. Sidecars, Microservices and Service Mesh

## Sidecar Containers

A **sidecar** is a helper container that runs **next to the main application container in the same pod**, sharing its network and storage.

- It adds supporting features such as **logging, proxying or monitoring** without changing the app's code.
- A common example is **Envoy** as a sidecar proxy in a service mesh (such as Istio). Envoy handles all traffic in and out of the app container and adds load balancing, retries and security.
- The application code stays simple, while the sidecar takes on the complex networking work.

> Hands-on sidecar and ambassador pods are in [CKAD](../02-CKAD/README.md).

## Monolithic vs Microservices Architecture

| | Monolithic | Microservices |
|---|---|---|
| Structure | One large application: UI, business logic and data access tightly joined and run as one unit | Many small, independent services that talk over the network |
| Getting started | Simpler to build at first | More moving parts from day one |
| Scaling and updates | Must scale and redeploy the whole app | Each service is developed, deployed and scaled separately |
| Failures | One bug can bring down everything | Faults stay isolated to one service |
| Best for | Small, simple apps | Large, complex systems |

## Service Mesh

A **service mesh** is a dedicated infrastructure layer that manages **service-to-service communication** in a microservices architecture: securely, reliably and observably, **without changing application code**.

- It deploys lightweight **sidecar proxies** (such as Envoy) next to every service instance.
- The proxies handle **traffic routing, load balancing, encryption (mTLS), retries, timeouts and monitoring**.
- **Istio** is a popular example.

Developers focus on business logic, while the mesh enforces communication policies, improving security, observability and traffic control.
