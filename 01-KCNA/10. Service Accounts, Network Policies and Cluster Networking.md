# 10. Service Accounts, Network Policies and Cluster Networking

## ServiceAccount

A **ServiceAccount** is an identity for **applications running inside pods**, not for humans. Controllers, jobs and custom apps use it to talk to the Kubernetes API securely.

- When a pod uses a ServiceAccount, Kubernetes automatically **mounts a token** inside the pod.
- The app uses that token to authenticate to the API Server.
- **RBAC** (RoleBindings or ClusterRoleBindings) then decides what the ServiceAccount may do, such as reading ConfigMaps or creating resources.

## NetworkPolicy

A NetworkPolicy is a **firewall for pods**: it controls which pods can talk to each other.

- By default, **all pods can talk to all pods**.
- A NetworkPolicy restricts traffic by **pod labels, namespaces and ports**, for example: *"Only frontend pods can talk to backend pods on port 80."*
- This limits how far an attack can spread inside the cluster.
- The cluster must use a network plugin that supports NetworkPolicies, such as **Calico** or **Cilium**.

## Cluster Networking

Cluster networking is how pods, nodes and services communicate. Kubernetes uses a **flat network model**: every pod gets its own IP, and pods talk to each other **without NAT**, whatever node they're on.

Three communication paths:

1. **Pod to pod** (also across nodes)
2. **Pod to service**, using stable virtual IPs
3. **External to cluster**, through NodePort, LoadBalancer or Ingress

CNI plugins (Flannel, Calico, Cilium) build this network. It is open by default, which is why NetworkPolicies are needed for security.

Reference: [Ports and protocols used by Kubernetes](https://kubernetes.io/docs/reference/networking/ports-and-protocols/)

## Pod Networking: Three Rules

**1. Each pod has its own IP address.**
Pods connect to each other directly by IP, without address rewriting.

```
pod-1: 10.244.1.10
pod-2: 10.244.1.20   → they can connect directly
```

**2. Pods on the same node communicate freely.**
Each pod gets a virtual Ethernet interface, and the node connects them through a virtual bridge (such as `cni0`), with no extra configuration.

**3. Pods on different nodes also communicate directly.**
The CNI plugin builds a cluster-wide overlay network (or BGP routes) and routing rules on every node.

```
pod-A on node-1: 10.244.1.5
pod-B on node-2: 10.244.2.8   → still reachable by IP
```

| Component | Responsibility |
|---|---|
| CNI plugin (Flannel, Calico) | Creates pod networks, assigns IPs, routes across nodes |
| kubelet | Attaches pods to the right network |
| Virtual bridge (`cni0`) | Routes traffic between pods on the same node |
| Overlay network or BGP routing | Carries traffic between pods on different nodes |

**Analogy:** every pod is a phone with its own number. Phones in the same room talk directly; phones in different rooms are joined by invisible wires (the CNI plugin), so they can still dial each other directly.
