# 08. Multiple Schedulers

## What Are Multiple Schedulers?

By default Kubernetes ships with **one scheduler** (`kube-scheduler`), the traffic manager that decides which pod goes to which node. You can run **more than one scheduler** in the same cluster, each with its own rules for choosing nodes.

## Use Cases

**1. Special placement for certain pods**

- AI/ML pods that must run only on **GPU nodes**
- test pods that should go to **low-cost nodes**
- custom business rules, such as placing pods only on nodes with specific labels

**2. Resource optimization**

- The default scheduler is overloaded and slow to place pods.
- You want to separate **critical workloads** (customer-facing apps) from **low-priority jobs** (data crunching).

Running two schedulers, one for high-priority and one for background jobs, avoids conflicts and improves efficiency.

## How It Works

1. In the pod YAML, name the scheduler that should handle it:
   ```yaml
   spec:
     schedulerName: my-custom-scheduler
   ```
2. That scheduler reads the pod and applies its own logic to pick a node.
3. Only that scheduler handles the pod; the others ignore it.

You can run the default `kube-scheduler` alongside one or more custom schedulers (written in Go or Python, or open-source ones). Each listens for its own pods.

**Analogy:** a school with one counsellor for science students and another for arts students. Each student (pod) goes to the counsellor (scheduler) named in their file (`schedulerName`).

## Advantages

| Feature | Benefit |
|---|---|
| Customized placement | Apply your own rules for where pods run |
| Specialized scheduling | Different schedulers for AI, batch jobs, front-end apps |
| Better resource management | Avoid overloading nodes |
| Faster scheduling | Work is shared between schedulers |
| Safer clustering | High- and low-priority workloads stay isolated |
