# 28. Volumes: hostPath and emptyDir

## What Are Volumes?

A container's own filesystem (its writable layer) is **ephemeral**: when the container crashes or is rescheduled, its data is lost. A **volume** is storage defined at the **pod level** that outlives individual containers and can be **shared between containers** in the same pod. Volumes support caching, shared files and stateful apps.

## Common Volume Types

| Type | What it is |
|---|---|
| `emptyDir` | Temporary storage that exists only as long as the pod |
| `hostPath` | A file or directory from the **node's** filesystem mounted into the pod |
| `persistentVolumeClaim` | External storage (AWS EBS, GCE PD, NFS) through Persistent Volumes, see [topic 29](29.%20Persistent%20Volumes%20and%20Claims.md) |
| `configMap` / `secret` | Configuration and credentials mounted as files |
| CSI volumes | Storage from external vendors through **Container Storage Interface** drivers, with dynamic provisioning |

## How a Container's Data Reaches External Storage

The pod spec declares a **volume source**, and each container declares a **volumeMount** path (such as `/data`). The container writes to `/data` as if it were local; Kubernetes routes the writes to the real backend: a node directory, an NFS share or a cloud disk.

## Replication and Multi-Node Clusters

- Storage systems such as cloud block storage, **Ceph** or **GlusterFS** can **replicate** data across storage nodes automatically, giving high availability and disaster recovery with no extra steps in Kubernetes.
- In multi-node clusters, pods can move between nodes, so use **network-attached or distributed volumes**: **ReadWriteMany** claims (NFS, GlusterFS), **CSI drivers** with dynamic provisioning, or storage platforms such as **Portworx, Rook or Longhorn**. They handle replication, locking and recovery so data stays consistent wherever the pod runs.

## Lab 1: hostPath

Create a file on the Minikube node:

```console
[ahmad@client1 ~]$ minikube ssh
docker@minikube:/$ sudo mkdir /etc/host-dir
docker@minikube:/etc$ echo "my name is ahmad hassan" | sudo tee /etc/host-dir/data.txt
my name is ahmad hassan
docker@minikube:/etc/host-dir$ cat data.txt
my name is ahmad hassan
```

Mount that directory into a pod that prints the file:

```yaml
# volume-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: hostpath-volume
spec:
  restartPolicy: OnFailure
  containers:
  - name: busybox
    image: busybox:stable
    command: ['sh', '-c', 'cat /data/data.txt']
    volumeMounts:
    - name: cloudops-host-data
      mountPath: /data
  volumes:
  - name: cloudops-host-data
    hostPath:
      path: /etc/host-dir
      type: Directory
```

```console
[ahmad@client1 volumes]$ kubectl apply -f volume-pod.yaml
pod/hostpath-volume created
[ahmad@client1 volumes]$ kubectl get po
NAME              READY   STATUS      RESTARTS   AGE
hostpath-volume   0/1     Completed   0          39s
[ahmad@client1 volumes]$ kubectl logs hostpath-volume
my name is ahmad hassan
```

The container read a file that lives on the **node**.

## Lab 2: emptyDir

```yaml
# empty-dir-volume-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: emptydir-volume-test
spec:
  restartPolicy: OnFailure
  containers:
  - name: busybox
    image: busybox:stable
    command: ['sh', '-c', 'echo "I am testing Empty Dir Volume Type" > /data/new.txt']
    volumeMounts:
    - name: empty-dir-volume
      mountPath: /data
  volumes:
  - name: empty-dir-volume
    emptyDir: {}
```

```console
[ahmad@client1 volumes]$ kubectl apply -f empty-dir-volume-pod.yaml
pod/emptydir-volume-test created
[ahmad@client1 volumes]$ kubectl get po
NAME                   READY   STATUS      RESTARTS   AGE
emptydir-volume-test   0/1     Completed   0          3s
hostpath-volume        0/1     Completed   0          5m47s
[ahmad@client1 volumes]$ kubectl logs emptydir-volume-test
(no output)
```

**Why no data?** The command only **writes** the file, so there is nothing in the logs, and the pod exits right after. An `emptyDir` lives only as long as its pod; when the pod finishes or is deleted, the data is gone. It's ideal for scratch space shared between containers (as in the [sidecar lab](03.%20Multi-Container%20Pods%20-%20Sidecar%20and%20Ambassador.md)), not for keeping data.

## Why hostPath Is Risky in Multi-Node Clusters

`hostPath` stores data on **one specific node's** disk. If the pod is rescheduled to another node (after a failure or scaling), the new node doesn't have that data. That breaks availability and consistency, so `hostPath` is unsuitable for production or distributed environments. Use Persistent Volumes backed by network or cloud storage instead.
