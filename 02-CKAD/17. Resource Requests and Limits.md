# 17. Resource Requests and Limits

## Key Concepts

**1. What are resource requirements?**
They define how much CPU and memory a container needs, using **requests** (the guaranteed minimum) and **limits** (the maximum it may use). They help Kubernetes schedule and manage pods efficiently.

**2. How does the scheduler use them?**
The scheduler places a pod using its **requests**: it picks a node with enough unallocated CPU and memory. **Limits are not used for scheduling.**

**3. Pod or container?**
Requests and limits are set **per container**. The scheduler adds up all containers' requests to place the pod.

**4. What if there aren't enough resources?**
If no node can satisfy the requests, the pod stays **Pending**.

**5. What do `Mi` and `Gi` mean?**
Binary memory units: **1Mi = 1,048,576 bytes (2^20)** and **1Gi = 1,073,741,824 bytes (2^30)**. They differ from MB/GB, which use powers of 10.

**6. How are limits expressed?**
CPU in cores or **millicores** (`500m` = 0.5 CPU); memory in `Mi`/`Gi`.

**7. If no limit is set, does the request become the limit?**
No. Without a limit, the container can use more than its request if resources are free. A namespace **LimitRange** can, however, apply default limits automatically.

**8. What happens when a limit is exceeded?**

| Resource | Over the limit |
|---|---|
| **CPU** | The container is **throttled** (slowed down) |
| **Memory** | The container is **killed** (`OOMKilled`) and usually restarted |

## Lab 1: CPU Requests and Limits

```yaml
# cpu-res-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: cloudops-pod
spec:
  containers:
  - name: ubuntu-container
    image: ubuntu
    resources:
      limits:
        cpu: 2
      requests:
        cpu: 1
```

```console
[root@client1 ahmad]# kubectl apply -f cpu-res-pod.yaml
pod/cloudops-pod created
[root@client1 ahmad]# kubectl get po
NAME           READY   STATUS             RESTARTS      AGE
cloudops-pod   0/1     CrashLoopBackOff   3 (48s ago)   100s
[root@client1 ahmad]# kubectl get po
NAME           READY   STATUS      RESTARTS      AGE
cloudops-pod   0/1     Completed   4 (60s ago)   112s
[root@client1 ahmad]# kubectl get po
NAME           READY   STATUS             RESTARTS      AGE
cloudops-pod   0/1     CrashLoopBackOff   4 (33s ago)   2m19s
```

The resources are fine; the problem is that a bare `ubuntu` container has nothing to run, so it exits straight away and restarts in a loop (see [topic 12](12.%20Commands%20and%20Arguments.md)). Give it a long-running command:

```yaml
spec:
  containers:
  - name: ubuntu-container
    image: ubuntu
    command:
      - sleep
      - "3600"
    resources:
      limits:
        cpu: 2
      requests:
        cpu: 1
```

```console
[root@client1 ahmad]# kubectl replace --force -f cpu-res-pod.yaml
pod "cloudops-pod" deleted
pod/cloudops-pod replaced
[root@client1 ahmad]# kubectl get po
NAME           READY   STATUS    RESTARTS   AGE
cloudops-pod   1/1     Running   0          18s
```

It now keeps running for 3600 seconds.

## Lab 2: A Memory Request Too Big for Any Node

```yaml
# mem-stress-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: mem-stress-pod
spec:
  containers:
  - name: memory-stress
    image: polinux/stress
    command:
    - stress
    args:
    - "--vm"
    - "1"
    - "--vm-bytes"
    - "15M"
    - "--vm-hang"
    - "1"
    resources:
      limits:
        memory: 10Gi
      requests:
        memory: 5Gi
```

```console
[root@client1 ahmad]# kubectl apply -f mem-stress-pod.yaml
pod/mem-stress-pod created
[root@client1 ahmad]# kubectl get po
NAME             READY   STATUS    RESTARTS   AGE
cloudops-pod     1/1     Running   0          3m37s
mem-stress-pod   0/1     Pending   0          9s
```

```console
[root@client1 ahmad]# kubectl describe po mem-stress-pod
Node:             <none>
Status:           Pending
    Limits:
      memory:  10Gi
    Requests:
      memory:     5Gi
Conditions:
  Type           Status
  PodScheduled   False
QoS Class:                   Burstable
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  18s   default-scheduler  0/2 nodes are available: 1 Insufficient memory, 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }. preemption: 0/2 nodes are available: 1 No preemption victims found for incoming pod, 1 Preemption is not helpful for scheduling.
```

**Why Pending?** The worker node doesn't have 5Gi free (`Insufficient memory`), and the control-plane node is tainted. No node can satisfy the **request**, so the pod is never scheduled.

Lower the request and limit to realistic values:

```yaml
    resources:
      limits:
        memory: 100Mi
      requests:
        memory: 50Mi
```

```console
[root@client1 ahmad]# kubectl replace --force -f mem-stress-pod.yaml
pod "mem-stress-pod" deleted
pod/mem-stress-pod replaced
[root@client1 ahmad]# kubectl get po
NAME             READY   STATUS    RESTARTS   AGE
cloudops-pod     1/1     Running   0          7m20s
mem-stress-pod   1/1     Running   0          37s
```

The pod schedules and runs, using 15M of memory, safely under its 100Mi limit.

> Namespace-wide limits with `ResourceQuota` are covered in [topic 09](09.%20Namespaces%2C%20Contexts%20and%20Resource%20Quotas.md).
