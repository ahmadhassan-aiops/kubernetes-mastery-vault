# 24. Monitoring and Debugging

**Monitoring** collects metrics from cluster components (nodes, pods, containers). **Debugging** investigates runtime issues such as failed pods, crash loops or misconfigured resources. Kubernetes gives you native tools (`kubectl`, events, logs) and integrates with external observability systems. Debugging usually starts with status, configuration and logs; monitoring gives the big picture through dashboards and alerts.

## Debugging Tips: Status, Config and Logs

| Check | Commands | Look for |
|---|---|---|
| **Status** | `kubectl get pods`, `kubectl describe pod <pod>` | The phase (Pending, Running, CrashLoopBackOff) and the **Events** timeline at the bottom of `describe` |
| **Config** | `kubectl get configmap/secret <name> -o yaml`, `kubectl edit` | Wrong values, missing environment variables, wrong volume paths |
| **Logs** | `kubectl logs <pod> [-c container]` | Application errors; use `--previous` for a crashed container |

## Why External Monitoring Tools Matter

External tools aggregate and visualize data, raise alerts and show trends:

| Tool | Role |
|---|---|
| **Prometheus** | Metrics collection |
| **Grafana** | Dashboards |
| **ELK Stack / Loki** | Log aggregation |
| **Jaeger** | Distributed tracing |

They help SREs and developers spot anomalies early, track resource usage and correlate logs with application state, which is essential for production clusters.

## Metrics Server

The **Metrics Server** is a lightweight aggregator of resource usage:

- It scrapes CPU and memory data from each node's **kubelet** (the `/stats/summary` API) and exposes it through the Kubernetes API.
- Metrics are **not stored long-term**; they power the **Horizontal Pod Autoscaler** and `kubectl top`.
- It runs as its own Deployment and needs RBAC permissions and network access to the kubelets.

## The Kubelet and cAdvisor

The kubelet is the node agent that keeps containers running as described in their pod specs. It also collects performance data through **cAdvisor** (Container Advisor), which is built into the kubelet and gathers real-time CPU, memory, filesystem and network usage for every container. The Metrics Server reads these stats, so the kubelet matters for monitoring as well as for running containers.

## Monitoring in kind and Minikube

- **kind:** meant for local testing, so node metrics aren't available by default. Install the Metrics Server yourself (below); Prometheus and Grafana can be added with Helm.
- **Minikube:** better built-in support. `minikube addons enable metrics-server` turns on `kubectl top`, and add-ons make Prometheus and Grafana easy to try.

## Lab: Installing the Metrics Server on kind

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
```

kind's kubelets use self-signed certificates, so tell the Metrics Server to skip TLS verification:

```bash
kubectl patch deployment metrics-server -n kube-system \
  --type='json' \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
```

On Minikube instead:

```bash
minikube addons enable metrics-server
```
