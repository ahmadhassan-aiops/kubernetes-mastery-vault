# 03. Multi-Container Pods: Sidecar and Ambassador

## Why Run Several Containers in One Pod?

A pod can run **multiple containers**, from the same or different images. This is useful when containers are **tightly coupled** and need to share:

- **Networking:** they talk over `localhost`
- **Storage:** they share volumes

They are scheduled together on the same node and act as one unit. **All containers in a pod share the same fate:** same storage, same network, created and destroyed together.

This supports both styles: in a monolith, tightly integrated parts can share a pod; in microservices, a pod can hold the main service plus a helper (a proxy or a metrics exporter).

**Three common patterns:**

1. **Sidecar:** extends the main app (log shipping, syncing files)
2. **Ambassador:** proxies the app's connections to the outside world
3. **Adapter:** reformats the app's output (for example, standardizing logs or metrics)

## Pattern 1: Sidecar

The main container writes a file into a shared `emptyDir` volume; the sidecar reads it every 5 seconds.

```yaml
# sidecar-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sidecar-practice-pod
spec:
  containers:
    - name: main-container
      image: busybox:stable
      command: ['sh', '-c', 'echo "I am learning kubernetes" > /output-dir/data.txt; while true; do sleep 5; done']
      volumeMounts:
        - name: shared-volume
          mountPath: /output-dir

    - name: sidecar-container
      image: busybox:stable
      command: ['sh', '-c', 'while true; do cat /input-dir/data.txt; sleep 5; done']
      volumeMounts:
        - name: shared-volume
          mountPath: /input-dir

  volumes:
    - name: shared-volume
      emptyDir: {}
```

Cluster for this lab (one control plane, one worker):

```yaml
# config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
```

```console
[root@client1 ahmad]# kind create cluster --name my-cluster --config config.yaml
[root@client1 ahmad]# kubectl get nodes

my-cluster-control-plane   Ready    control-plane   74s   v1.32.2
my-cluster-worker          Ready    <none>          63s   v1.32.2
```

`2/2` means both containers are running:

```console

[root@client1 ahmad]# kubectl get pods -w

```

Read the **sidecar's** logs with `-c` to prove it can see the file written by the main container:

## Pattern 2: Ambassador

### Step 1: A web server behind a Service

```yaml
# ambassador.yaml
apiVersion: v1
kind: Pod
metadata:
  name: ambassador-webserver
  labels:
    app: ambassador-pod
spec:
  containers:
  - name: nginx
    image: nginx:stable
    ports:
    - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: ambassador-service
spec:
  selector:
    app: ambassador-pod
  ports:
  - protocol: TCP
    port: 8081
    targetPort: 80
```

```console
[root@client1 ahmad]# kubectl apply -f ambassador.yaml
pod/ambassador-webserver created
service/ambassador-service created

[root@client1 ahmad]# kubectl get po,svc
```

### Step 2: A client pod with an HAProxy ambassador

The main container only ever calls `localhost:8080`. The HAProxy ambassador container listens on 8080 and forwards to `ambassador-service:8081`.

```yaml
# ambassador-test.yaml
apiVersion: v1
kind: Pod
metadata:
  name: ambassador-test-pod
spec:
  containers:
  - name: main-container
    image: curlimages/curl
    command: ['sh', '-c', 'while true; do curl localhost:8080; sleep 5; done']
  - name: ambassador-container
    image: haproxy:2.4
    volumeMounts:
    - name: config
      mountPath: /usr/local/etc/haproxy/
  volumes:
  - name: config
    configMap:
      name: haproxy-config
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: haproxy-config
data:
  haproxy.cfg: |
    global
      maxconn 256

    defaults
      mode http
      timeout connect 5s
      timeout client  10s
      timeout server  10s

    frontend ambassador
      bind *:8080
      default_backend ambassador_service

    backend ambassador_service
      server svc ambassador-service:8081
```

```console
[root@client1 ahmad]# kubectl apply -f ambassador-test.yaml
pod/ambassador-test-pod created
configmap/haproxy-config created

[root@client1 ahmad]# kubectl get configmap
NAME               DATA   AGE
haproxy-config     1      93s
kube-root-ca.crt   1      17h

[root@client1 ahmad]# kubectl get pods
NAME                   READY   STATUS    RESTARTS      AGE
ambassador-test-pod    2/2     Running   0             8s
ambassador-webserver   1/1     Running   0             42m
sidecar-practice-pod   2/2     Running   2 (61m ago)   17h
```

### How the pieces fit

1. `ambassador-webserver` runs Nginx on port 80, exposed inside the cluster by `ambassador-service` on port **8081**.
2. In `ambassador-test-pod`, the curl container sends requests to `localhost:8080` in a loop.
3. The HAProxy container listens on 8080 and forwards those requests to `ambassador-service`, which reaches the web server.

The main container reaches the external service **indirectly**, through the ambassador. This pattern is used for traffic shaping, observability and service meshes.

> The theory behind sidecars and service meshes is in [KCNA topic 12](../01-KCNA/12.%20Sidecars%2C%20Microservices%20and%20Service%20Mesh.md).
