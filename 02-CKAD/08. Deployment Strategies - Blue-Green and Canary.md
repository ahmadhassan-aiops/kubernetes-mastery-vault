# 08. Deployment Strategies: Blue-Green and Canary

Both strategies run **two production environments** side by side and use **Service label selectors** to decide where traffic goes.

| Strategy | Idea |
|---|---|
| **Blue-Green** | Two identical environments: **blue = old**, **green = new**. Test green first, then switch **all** traffic from blue to green at once. |
| **Canary** | Old and new run together, but only a **small share of traffic** reaches the new version (for example 75% main, 25% canary). If all goes well, the canary becomes production. |

Both labs ran on the two-node `my-cluster` kind cluster:

```console
[root@client1 ahmad]# kubectl get nodes
NAME                       STATUS   ROLES           AGE   VERSION
my-cluster-control-plane   Ready    control-plane   41h   v1.32.2
my-cluster-worker          Ready    <none>          41h   v1.32.2
```

## 1. Blue-Green

### Step 1: Deploy blue (the current version)

```yaml
# blue-green-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: blue-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: bluegreen-test
      color: blue
  template:
    metadata:
      labels:
        app: bluegreen-test
        color: blue
    spec:
      containers:
      - name: nginx
        image: linuxacademycontent/ckad-nginx:blue
        ports:
        - containerPort: 80
```

```console
[root@client1 ahmad]# kubectl apply -f blue-green-deployment.yaml
deployment.apps/blue-deployment created
[root@client1 ahmad]# kubectl get po,rs,deploy
NAME                                   READY   STATUS              RESTARTS   AGE
pod/blue-deployment-5d4b49cdf9-55nl2   0/1     ContainerCreating   0          6s

NAME                                         DESIRED   CURRENT   READY   AGE
replicaset.apps/blue-deployment-5d4b49cdf9   1         1         0       6s

NAME                              READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/blue-deployment   0/1     1            0           6s
```

### Step 2: A Service that selects `color: blue`

```yaml
# blue-green-svc.yaml
apiVersion: v1
kind: Service
metadata:
  name: bluegreen-service
spec:
  selector:
    app: bluegreen-test
    color: blue
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80
```

```console
[root@client1 ahmad]# kubectl apply -f blue-green-svc.yaml
service/bluegreen-service created
[root@client1 ahmad]# kubectl get svc
NAME                TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
bluegreen-service   ClusterIP   10.96.90.236   <none>        80/TCP    16s
kubernetes          ClusterIP   10.96.0.1      <none>        443/TCP   15h
```

The Service finds the blue pod through its labels and forwards its port 80 to the pod's `containerPort: 80`. The endpoint is the blue pod's IP:

```console
[root@client1 ahmad]# kubectl describe svc bluegreen-service
Name:                     bluegreen-service
Selector:                 app=bluegreen-test,color=blue
Type:                     ClusterIP
IP:                       10.96.90.236
Port:                     <unset>  80/TCP
TargetPort:               80/TCP
Endpoints:                10.244.1.61:80

[root@client1 ahmad]# kubectl get pods -o wide
NAME                               READY   STATUS    RESTARTS   AGE   IP            NODE                NOMINATED NODE   READINESS GATES
blue-deployment-5d4b49cdf9-55nl2   1/1     Running   0          12m   10.244.1.61   my-cluster-worker   <none>           <none>
```

Test from inside the worker node (a kind node is a Docker container):

```console
[root@client1 ahmad]# docker exec -it my-cluster-worker bash
root@my-cluster-worker:/# curl 10.96.90.236
I'm Blue!
```

Because routing is purely label-based, we can switch later by changing only the selector, without deleting the Service.

### Step 3: Deploy green (the new version)

```yaml
# green-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: green-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: bluegreen-test
      color: green
  template:
    metadata:
      labels:
        app: bluegreen-test
        color: green
    spec:
      containers:
      - name: nginx
        image: linuxacademycontent/ckad-nginx:green
        ports:
        - containerPort: 80
```

```console
[root@client1 ahmad]# kubectl apply -f green-deployment.yaml
deployment.apps/green-deployment created
[root@client1 ahmad]# kubectl get deploy
NAME               READY   UP-TO-DATE   AVAILABLE   AGE
blue-deployment    1/1     1            1           23m
green-deployment   1/1     1            1           9s
```

All traffic still goes to blue, because the Service selector only matches `color: blue`.

### Step 4: Test green directly by pod IP

```console
[root@client1 ahmad]# kubectl get pods -o wide
NAME                               READY   STATUS    RESTARTS   AGE     IP            NODE                NOMINATED NODE   READINESS GATES
blue-deployment-5d4b49cdf9-55nl2   1/1     Running   0          27m     10.244.1.61   my-cluster-worker   <none>           <none>
green-deployment-9774b9dbf-8dblq   1/1     Running   0          3m43s   10.244.1.62   my-cluster-worker   <none>           <none>
[root@client1 ahmad]# docker exec -it my-cluster-worker bash
root@my-cluster-worker:/# curl 10.244.1.62
I'm green!
```

Green works, so we can redirect the traffic.

### Step 5: Switch the Service to green

Change `color: blue` to `color: green` in the Service selector:

```console
[root@client1 ahmad]# kubectl edit svc bluegreen-service
service/bluegreen-service edited

[root@client1 ahmad]# docker exec -it my-cluster-worker bash
root@my-cluster-worker:/# curl 10.96.90.236
I'm green!
```

The same Service IP now serves the green application. To roll back, switch the selector back to blue.

## 2. Canary

### Step 1: The main production deployment (3 replicas)

```yaml
# main-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: main-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: canary-test
      environment: main
  template:
    metadata:
      labels:
        app: canary-test
        environment: main
    spec:
      containers:
      - name: nginx
        image: linuxacademycontent/ckad-nginx:1.0.0
        ports:
        - containerPort: 80
```

```console
[root@client1 ahmad]# kubectl apply -f main-deployment.yaml

[root@client1 ahmad]# kubectl get po,deploy
```

### Step 3: Add the canary (1 replica)

```yaml
# canary-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: canary-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: canary-test
      environment: canary
  template:
    metadata:
      labels:
        app: canary-test
        environment: canary
    spec:
      containers:
      - name: nginx
        image: linuxacademycontent/ckad-nginx:canary
        ports:
        - containerPort: 80
```

**Where does traffic go now? To both.** The Service selects only `app: canary-test`, which both deployments carry; the `environment` label is ignored by the Service.

```console
[root@client1 ahmad]# kubectl apply -f canary-deployment.yaml

[root@client1 ahmad]# kubectl get po,svc,deploy

pod/main-deployment-648c8c68b4-hbn5m    1/1     Running   0          25m
pod/main-deployment-648c8c68b4-w92tb    1/1     Running   0          25m

NAME                      TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)   AGE
service/canary-test-svc   ClusterIP   10.96.2.10   <none>        80/TCP    20m
```

One more endpoint: 3 main pods + 1 canary pod, so roughly **25% of requests** reach the canary:


### Step 4: Promote the canary

Add `environment: canary` to the Service selector:

```console
[root@client1 ahmad]# kubectl edit svc canary-test-svc
service/canary-test-svc edited
[root@client1 ahmad]# kubectl describe svc canary-test-svc
Selector:                 app=canary-test,environment=canary
Endpoints:                10.244.1.67:80
```

Only one endpoint now, and every request reaches the canary:

```console
root@my-cluster-worker:/# curl 10.96.2.10
I'm the canary!
root@my-cluster-worker:/# curl 10.96.2.10
I'm the canary!
root@my-cluster-worker:/# curl 10.96.2.10
I'm the canary!
```

## Key Takeaway

**Services route by labels.** Changing a Service's selector is all it takes to switch (blue-green) or split (canary) traffic between versions. The traffic split in a canary follows the **ratio of pod replicas**.
