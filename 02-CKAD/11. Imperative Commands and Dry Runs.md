# 11. Imperative Commands and Dry Runs

**Imperative commands** create, update or delete resources straight from the command line, without writing YAML first. For example, `kubectl create deployment nginx --image=nginx` creates a Deployment immediately.

The **declarative** approach instead describes the desired state in YAML and applies it with `kubectl apply -f`. Imperative commands are great for quick prototyping, scripting and the CKAD exam; declarative files are easier to maintain in production.

> The full command reference is in the [kubectl cheat sheet](30.%20kubectl%20Command%20Cheat%20Sheet.md). Theory is in [KCNA topic 05](../01-KCNA/05.%20Imperative%20vs%20Declarative.md).

## Running a Pod

```console
[root@client1 ahmad]# kubectl run cloudops-pod --image nginx
pod/cloudops-pod created
[root@client1 ahmad]# kubectl get pods
NAME           READY   STATUS    RESTARTS   AGE
cloudops-pod   1/1     Running   0          5s
```

## Dry Runs: Generate YAML Without Creating Anything

`--dry-run=client` validates the command but creates nothing:

```console
[root@client1 ahmad]# kubectl run test-pod --image redis --dry-run=client
pod/test-pod created (dry run)
[root@client1 ahmad]# kubectl get pods
NAME           READY   STATUS    RESTARTS   AGE
cloudops-pod   1/1     Running   0          61s
```

Add `-o yaml` to print the manifest, and redirect it to a file as a starting template:

```console
[root@client1 ahmad]# kubectl run test-pod --image redis --dry-run=client -o yaml > test-pod.yaml
[root@client1 ahmad]# cat test-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: null
  labels:
    run: test-pod
  name: test-pod
spec:
  containers:
  - image: redis
    name: test-pod
    resources: {}
  dnsPolicy: ClusterFirst
  restartPolicy: Always
status: {}
```

`-o json` gives the same object in JSON:

```console
[root@client1 ahmad]# kubectl run test-pod --image redis --dry-run=client -o json
{
    "kind": "Pod",
    "apiVersion": "v1",
    "metadata": {
        "name": "test-pod",
        "creationTimestamp": null,
        "labels": {
            "run": "test-pod"
        }
    },
    "spec": {
        "containers": [
            {
                "name": "test-pod",
                "image": "redis",
                "resources": {}
            }
        ],
        "restartPolicy": "Always",
        "dnsPolicy": "ClusterFirst"
    },
    "status": {}
}
```

## Deployments

```console
[root@client1 ahmad]# kubectl create deploy my-deploy --image nginx --replicas 3 --dry-run=client
deployment.apps/my-deploy created (dry run)
[root@client1 ahmad]# kubectl get deploy
No resources found in default namespace.

[root@client1 ahmad]# kubectl create deploy my-deploy --image nginx --replicas 3 --dry-run=client -o yaml > test-deploy.yaml
[root@client1 ahmad]# cat test-deploy.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  creationTimestamp: null
  labels:
    app: my-deploy
  name: my-deploy
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-deploy
  strategy: {}
  template:
    metadata:
      creationTimestamp: null
      labels:
        app: my-deploy
    spec:
      containers:
      - image: nginx
        name: nginx
        resources: {}
status: {}
```

Edit the generated file as needed, then `kubectl apply -f` it. Or create the Deployment directly:

```console
[root@client1 ahmad]# kubectl create deploy my-deploy --image nginx --replicas 3
[root@client1 ahmad]# kubectl get deploy
NAME        READY   UP-TO-DATE   AVAILABLE   AGE
my-deploy   3/3     3            3           2m55s
[root@client1 ahmad]# kubectl get pods
NAME                         READY   STATUS    RESTARTS   AGE
cloudops-pod                 1/1     Running   0          18m
my-deploy-74b6755685-ccnbn   1/1     Running   0          4m15s
my-deploy-74b6755685-sr86s   1/1     Running   0          4m15s
my-deploy-74b6755685-wbjbf   1/1     Running   0          4m15s
```

## Services: `expose` vs `create svc`

### `kubectl expose` uses the pod's labels

```console
[root@client1 ahmad]# kubectl expose pod cloudops-pod --port 6379 --name redis-service --dry-run=client
service/redis-service exposed (dry run)
[root@client1 ahmad]# kubectl expose pod cloudops-pod --port 6379 --name redis-service
service/redis-service exposed
[root@client1 ahmad]# kubectl describe svc redis-service
Name:                     redis-service
Namespace:                default
Labels:                   run=cloudops-pod
Selector:                 run=cloudops-pod
Type:                     ClusterIP
IP:                       10.96.245.233
Port:                     <unset>  6379/TCP
TargetPort:               6379/TCP
Endpoints:                10.244.1.69:6379
```

The selector `run=cloudops-pod` was copied from the pod (`kubectl run` adds the `run=<name>` label), so the Service got an **endpoint** straight away:

```console
[root@client1 ahmad]# kubectl describe po cloudops-pod
Name:             cloudops-pod
Node:             my-cluster-worker/172.25.0.3
Labels:           run=cloudops-pod
Status:           Running
IP:               10.244.1.69
```

### `kubectl create svc` assumes `app=<name>`

```console
[root@client1 ahmad]# kubectl create svc clusterip redis --tcp=6379:6379 --dry-run=client -o yaml > test-service2.yaml
[root@client1 ahmad]# cat test-service2.yaml
apiVersion: v1
kind: Service
metadata:
  creationTimestamp: null
  labels:
    app: redis
  name: redis
spec:
  ports:
  - name: 6379-6379
    port: 6379
    protocol: TCP
    targetPort: 6379
  selector:
    app: redis
  type: ClusterIP
status:
  loadBalancer: {}

[root@client1 ahmad]# kubectl apply -f test-service2.yaml
service/redis created
[root@client1 ahmad]# kubectl get svc
NAME            TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)    AGE
kubernetes      ClusterIP   10.96.0.1       <none>        443/TCP    2d15h
redis           ClusterIP   10.96.168.231   <none>        6379/TCP   8s
redis-service   ClusterIP   10.96.245.233   <none>        6379/TCP   5m48s
[root@client1 ahmad]# kubectl describe svc redis
Name:                     redis
Selector:                 app=redis
Type:                     ClusterIP
IP:                       10.96.168.231
Port:                     6379-6379  6379/TCP
TargetPort:               6379/TCP
Endpoints:
```

### Why the second Service has no endpoint

`kubectl create svc` can't take a selector; it always assumes `app=<service-name>`. No pod carries `app=redis`, so the Service has **no endpoint** and doesn't work. Imperative commands are fast, but they don't check that matching pods exist.

| Command | Selector | NodePort |
|---|---|---|
| `kubectl expose` | Uses the pod's labels automatically | Can't set a specific nodePort |
| `kubectl create service` | Assumes `app=<name>`, can't be changed | Can set `--node-port` |

**Tip:** prefer `kubectl expose`. If you need a specific nodePort, generate YAML with `--dry-run=client -o yaml`, add the nodePort, then apply.
