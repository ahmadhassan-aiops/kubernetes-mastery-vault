# 29. Persistent Volumes and Claims

## Persistent Volume (PV)

A **PV** is a piece of storage provided to the cluster, like a USB drive already plugged in and ready to use. It can be a node disk, network storage (NFS, iSCSI) or cloud block storage (AWS EBS, GCP Persistent Disk, Azure Disk).

**A PV lives independently of any pod**, so its data survives when pods are deleted or crash.

- A **cluster-wide** resource, defined by admins, not tied to a pod
- **Pre-provisioned** (static) or **dynamically** provisioned
- Many backends: `hostPath`, `nfs`, `gcePersistentDisk`, `awsElasticBlockStore`, ...

| Access mode | Short | Meaning |
|---|---|---|
| `ReadWriteOnce` | RWO | One node can read and write |
| `ReadOnlyMany` | ROX | Many nodes can read |
| `ReadWriteMany` | RWX | Many nodes can read and write |

## Persistent Volume Claim (PVC)

A **PVC** is an application's **request for storage**: "I need 1Gi, ReadWriteOnce." Kubernetes finds a matching PV and **binds** them. Developers don't need to know where the storage physically lives.

A PVC can specify the **size**, **access mode** and **storage class** (for dynamic provisioning).

**Analogy:** a PV is a storage room; a PVC is someone asking for a room of a certain size with certain features. Kubernetes matches them and hands over the key.

## How They Work Together

| | |
|---|---|
| **PV** | The supply |
| **PVC** | The demand |
| **Binding** | Automatic matching on size, access mode and storage class; exclusive once bound |

1. An admin (or a dynamic provisioner) creates PVs.
2. A user creates a PVC.
3. Kubernetes finds a suitable PV and binds it; the PV becomes **Bound**.
4. A pod uses the PVC through `volumes` and `volumeMounts`.
5. The pod reads and writes persistent data.

**Why use them?** Data outlives pods, storage is managed separately from apps, volumes can be provisioned automatically, and it works the same in cloud and on-premises clusters.

```yaml
# PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: myclaim
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
---
# pod using the PVC
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  containers:
  - name: app
    image: busybox
    command: [ "sleep", "3600" ]
    volumeMounts:
    - mountPath: "/data"
      name: mypd
  volumes:
  - name: mypd
    persistentVolumeClaim:
      claimName: myclaim
```

> A pod never uses a PV directly. **To use a PV, you need a PVC.**

## Lab Part 1: Logs That Vanish

`kodekloud/event-simulator` with `LOG_HANDLERS=file` writes its log to `/log/app.log` inside the container:

```yaml
# pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: cloudops-webapp
spec:
  containers:
  - name: event-simulator
    image: kodekloud/event-simulator
    env:
    - name: LOG_HANDLERS
      value: file
```

```console
[ahmad@client1 volumes]$ kubectl apply -f pod.yaml
pod/cloudops-webapp created
[ahmad@client1 volumes]$ kubectl exec -it cloudops-webapp -- /bin/sh
/ # ls
bin                 event-simulator.py  log                 proc                sbin                tmp
dev                 home                media               root                srv                 usr
etc                 lib                 mnt                 run                 sys                 var
/ # cd log
/log # ls
app.log
```

```bash
kubectl exec cloudops-webapp -- cat /log/app.log
```

The logs are visible **only while the pod runs**; once it's rescheduled or deleted, they're gone.

## Lab Part 3: PV and PVC Binding

### A static PV

```yaml
# pv.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-log
  labels:
    name: vol
spec:
  persistentVolumeReclaimPolicy: Retain
  accessModes:
    - ReadWriteMany
  capacity:
    storage: 100Mi
  hostPath:
    path: /mnt/data
```

```console
[ahmad@client1 ~]$ kubectl apply -f pv.yaml
persistentvolume/pv-log created
[ahmad@client1 ~]$ kubectl get pv
NAME     CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM   STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
pv-log   100Mi      RWX            Retain           Available                          <unset>                          8s
```

### Surprise 1: the PVC ignores our PV

```yaml
# pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: claim-log-1
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 50Mi
```

```console
[ahmad@client1 ~]$ kubectl apply -f pvc.yaml
persistentvolumeclaim/claim-log-1 created
[ahmad@client1 ~]$ kubectl get pvc
NAME          STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
claim-log-1   Bound    pvc-41e0c7b8-3374-4282-a90f-d8f9c808fb65   50Mi       RWX            standard       <unset>                 12s
[ahmad@client1 ~]$ kubectl get pv
NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM                 STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
pv-log                                     100Mi      RWX            Retain           Available                                        <unset>                          6m44s
pvc-41e0c7b8-3374-4282-a90f-d8f9c808fb65   50Mi       RWX            Delete           Bound       default/claim-log-1   standard       <unset>                          2m42s
```

**Why?** Minikube has a **default StorageClass** (`standard`). The PVC didn't name a class, so it received `standard` and was **dynamically provisioned** a brand-new PV. Our static `pv-log` has no storage class, so it didn't match. For a PVC to bind to a specific PV, **access modes, size and `storageClassName` must all match**.

**Fix:** set `storageClassName: ""` in both the PV and the PVC, or disable the default StorageClass. Here I disabled it:

```console
[ahmad@client1 ~]$ minikube addons disable default-storageclass
* "The 'default-storageclass' addon is disabled
[ahmad@client1 ~]$ kubectl delete pvc claim-log-1
persistentvolumeclaim "claim-log-1" deleted
[ahmad@client1 ~]$ kubectl get pv
NAME     CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM   STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
pv-log   100Mi      RWX            Retain           Available                          <unset>                          12m
```

The dynamically provisioned PV was deleted along with its claim (its reclaim policy was `Delete`).

### Surprise 2: access modes must match

Change the PVC to `ReadWriteOnce` while the PV offers `ReadWriteMany`:

```console
[ahmad@client1 ~]$ kubectl apply -f pvc.yaml
persistentvolumeclaim/claim-log-1 created
[ahmad@client1 ~]$ kubectl get pv,pvc
NAME                      CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM   STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
persistentvolume/pv-log   100Mi      RWX            Retain           Available                          <unset>                          14m

NAME                                STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
persistentvolumeclaim/claim-log-1   Pending                                                     <unset>                 14s
```

**Pending**: no PV matches the requested access mode.

### Successful binding

Set the PVC back to `ReadWriteMany`:

```console
[ahmad@client1 ~]$ kubectl delete pvc claim-log-1
[ahmad@client1 ~]$ kubectl apply -f pvc.yaml
persistentvolumeclaim/claim-log-1 created
[ahmad@client1 ~]$ kubectl get pvc
NAME          STATUS   VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
claim-log-1   Bound    pv-log   100Mi      RWX                           <unset>                 5s
[ahmad@client1 ~]$ kubectl get pv
NAME     CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM                 STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
pv-log   100Mi      RWX            Retain           Bound    default/claim-log-1                  <unset>                          17m
```

Notice the PVC asked for 50Mi but got the **whole 100Mi** PV: binding is one-to-one.

### Surprise 3: Retain keeps the PV out of reach

```console
[ahmad@client1 ~]$ kubectl delete pvc claim-log-1
persistentvolumeclaim "claim-log-1" deleted
[ahmad@client1 ~]$ kubectl get pv
NAME     CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM                 STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
pv-log   100Mi      RWX            Retain           Released   default/claim-log-1                  <unset>                          19m

[ahmad@client1 ~]$ kubectl apply -f pvc.yaml
[ahmad@client1 ~]$ kubectl get pvc
NAME          STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
claim-log-1   Pending                                                     <unset>                 80s
```

**Why Pending again?** With `persistentVolumeReclaimPolicy: Retain`, the PV keeps its data after the claim is deleted and moves to **Released**. Kubernetes won't hand a Released volume to a new claim until an admin cleans the data and makes it Available again (by editing or recreating the PV). This protects logs, backups and audit records from accidental reuse.

### A fresh PV gets picked up automatically

```yaml
# pv2.yaml (same spec, new name)
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-log-2
  labels:
    name: vol
spec:
  persistentVolumeReclaimPolicy: Retain
  accessModes:
    - ReadWriteMany
  capacity:
    storage: 100Mi
  hostPath:
    path: /mnt/data
```

```console
[ahmad@client1 ~]$ kubectl apply -f pv2.yaml
persistentvolume/pv-log-2 created
[ahmad@client1 ~]$ kubectl get pvc
NAME          STATUS   VOLUME     CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
claim-log-1   Bound    pv-log-2   100Mi      RWX                           <unset>                 6m1s
[ahmad@client1 ~]$ kubectl get pv
NAME       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM                 STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
pv-log     100Mi      RWX            Retain           Released   default/claim-log-1                  <unset>                          27m
pv-log-2   100Mi      RWX            Retain           Bound      default/claim-log-1                  <unset>                          56s
```

The waiting PVC bound to the new, clean `pv-log-2` straight away, while the old Released PV stayed untouched.

## Reclaim Policies

| Policy | After the PVC is deleted |
|---|---|
| `Retain` | PV becomes **Released**; data is kept; manual cleanup needed |
| `Delete` | PV and its underlying storage are deleted (typical for dynamic provisioning) |
| `Recycle` | Deprecated: basic wipe, then Available again |
