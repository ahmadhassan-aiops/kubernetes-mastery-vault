# 16. Service Accounts and RBAC

## Key Questions Answered

**1. What is a Service Account?**
A Service Account (SA) gives **pods an identity** so they can talk securely to the Kubernetes API or other services. User accounts are for humans; service accounts are for apps inside the cluster.

**2. What about the token and the Secret?**
Kubernetes used to create a Secret automatically for every service account, holding a **token (a JWT)** that was mounted into the pod. The app used it to prove its identity to the API.

**3. How do pods use the token?**
A pod reads the token from `/var/run/secrets/kubernetes.io/serviceaccount/token` and sends it with its API requests. Kubernetes identifies the SA from the token and authorizes the request using **RBAC** rules.

**4. What about access from outside the cluster?**
An external tool can use a service account token passed with its API requests. This is a security risk if the token isn't rotated or protected.

**5. Why is there a default Service Account?**
Every namespace has a `default` SA, used by any pod that doesn't name one. It has very limited permissions unless you grant more through RBAC, which keeps things secure by default.

**6. What changed in v1.22 and v1.24?**
Kubernetes **stopped auto-generating long-lived token Secrets** for service accounts. Pods now get **short-lived, auto-rotated projected tokens**, and you request tokens explicitly (`kubectl create token`). If you really need a long-lived one, create a Secret of type `kubernetes.io/service-account-token`. This reduces the risk of leaked or abused tokens.

**7. Can a token have a very long expiry?**
Yes, by requesting a large `expirationSeconds` through the TokenRequest API, but it's discouraged: tokens should be short-lived and rotated.

**8. What is jwt.io?**
A website that decodes a JWT so you can see its issuer, expiry and claims. Service account tokens are JWTs, so it helps you understand what Kubernetes puts in them.

## Lab: A Dashboard That Needs Permission to List Pods

```console
[root@client1 ahmad]# kubectl get sa
NAME      SECRETS   AGE
default   0         6d20h
```

### Step 1: Deploy the dashboard

```yaml
# my-dashboard.yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-dashboard
  labels:
    app: dashboard
spec:
  containers:
  - name: web-dashboard
    image: gcr.io/kodekloud/customimage/my-kubernetes-dashboard
    ports:
    - containerPort: 8080
      protocol: TCP
    env:
    - name: PYTHONUNBUFFERED
      value: "1"
```

```yaml
# my-dashboard-svc.yaml
apiVersion: v1
kind: Service
metadata:
  name: dashboard-svc
  labels:
    app: dashboard
spec:
  selector:
    app: dashboard
  type: NodePort
  ports:
  - port: 8080
    targetPort: 8080
    protocol: TCP
```

```console
[root@client1 ahmad]# kubectl apply -f my-dashboard.yaml
pod/my-dashboard created
[root@client1 ahmad]# kubectl apply -f my-dashboard-svc.yaml
service/dashboard-svc created
[root@client1 ahmad]# kubectl get svc
NAME            TYPE        CLUSTER-IP    EXTERNAL-IP   PORT(S)          AGE
dashboard-svc   NodePort    10.96.27.12   <none>        8080:31069/TCP   6s
kubernetes      ClusterIP   10.96.0.1     <none>        443/TCP          5d19h
[root@client1 ahmad]# kubectl get po
NAME           READY   STATUS    RESTARTS   AGE
my-dashboard   1/1     Running   0          8m23s

[root@client1 ahmad]# kubectl port-forward pod/my-dashboard 5555:8080
Forwarding from 127.0.0.1:5555 -> 8080
Forwarding from [::1]:5555 -> 8080
Handling connection for 5555
```

At `127.0.0.1:5555`, the dashboard **can't list pods**: it has no service-account-based permission yet.

### Step 2: Inspect the default Service Account

```console
[root@client1 ahmad]# kubectl describe sa default
Name:                default
Namespace:           default
Image pull secrets:  <none>
Mountable secrets:   <none>
Tokens:              <none>
```

No token Secret, as expected after v1.24. Yet the pod still uses the default SA through a **projected token volume**:

```console
[root@client1 ahmad]# kubectl describe po my-dashboard
Service Account:  default
...
    Mounts:
      /var/run/secrets/kubernetes.io/serviceaccount from kube-api-access-pz68r (ro)
Volumes:
  kube-api-access-pz68r:
    Type:                    Projected (a volume that contains injected data from multiple sources)
    TokenExpirationSeconds:  3607
    ConfigMapName:           kube-root-ca.crt
```

```console
[root@client1 ahmad]# kubectl exec -it my-dashboard -- ls /var/run/secrets/kubernetes.io/serviceaccount
ca.crt     namespace  token
[root@client1 ahmad]# kubectl exec -it my-dashboard -- cat /var/run/secrets/kubernetes.io/serviceaccount/token
eyJhbGciOiJSUzI1NiIsImtpZCI6...<JWT truncated>
```

All the pod's default, limited communication uses this token.

### Step 3: A dedicated Service Account

```console
[root@client1 ahmad]# kubectl create sa dashboard-sa
serviceaccount/dashboard-sa created
[root@client1 ahmad]# kubectl get sa
NAME           SECRETS   AGE
dashboard-sa   0         6s
default        0         6d20h
```

### Step 4: A Role that can read pods

```yaml
# dashboard-role.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]
  resources:
  - pods
  verbs:
  - get
  - watch
  - list
```

```console
[root@client1 ahmad]# kubectl apply -f dashboard-role.yaml
role.rbac.authorization.k8s.io/pod-reader created
[root@client1 ahmad]# kubectl get role
NAME         CREATED AT
pod-reader   2025-05-06T12:31:04Z
```

### Step 5: Bind the Role to the Service Account

```yaml
# dashboard-rbac.yaml
kind: RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
metadata:
  name: read-pods
  namespace: default
subjects:
- kind: ServiceAccount
  name: dashboard-sa        # names are case sensitive
  namespace: default
roleRef:
  kind: Role                # must be Role or ClusterRole
  name: pod-reader          # must match the Role or ClusterRole name
  apiGroup: rbac.authorization.k8s.io
```

```console
[root@client1 ahmad]# kubectl apply -f dashboard-rbac.yaml
rolebinding.rbac.authorization.k8s.io/read-pods created
[root@client1 ahmad]# kubectl get rolebindings
NAME        ROLE              AGE
read-pods   Role/pod-reader   12s
```

### Step 6: Generate a token and use it

```console
[root@client1 ahmad]# kubectl create token dashboard-sa
eyJhbGciOiJSUzI1NiIsImtpZCI6...<JWT truncated>
```

Paste this token into the dashboard at `127.0.0.1:5555`, and it now lists **all pods**, including new ones:

```bash
kubectl run new-pod --image nginx    # appears in the dashboard straight away
```

**Flow:** ServiceAccount → RoleBinding → Role (`get`, `watch`, `list` pods) → token → the app can read pods.

> To attach the SA to a pod permanently instead of pasting a token, set `spec.serviceAccountName: dashboard-sa` in the pod spec. Theory on RBAC and authorization modes is in [KCNA topic 09](../01-KCNA/09.%20Authentication%20and%20Authorization.md).
