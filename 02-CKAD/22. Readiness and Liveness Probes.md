# 22. Readiness and Liveness Probes

**Probes** are health checks the kubelet runs against containers. They decide whether a container is ready for traffic or needs a restart.

| Probe | Question | If it fails |
|---|---|---|
| **Liveness** | Is the container alive? | Kubernetes **restarts** the container |
| **Readiness** | Is it ready to serve requests? | The pod is **removed from Service endpoints** (not restarted) |
| **Startup** | Has a slow app finished starting? | Liveness and readiness checks are **paused** until it succeeds |

## Probe Methods (Same for All Probes)

1. **HTTP GET:** request a path and port; a response in the **200 to 399** range means success.
2. **TCP socket:** try to open a TCP connection to a port; success means healthy.
3. **Exec command:** run a command in the container; **exit code 0** means healthy.

## Important Parameters

| Parameter | Meaning |
|---|---|
| `initialDelaySeconds` | Wait before the first probe |
| `periodSeconds` | Time between probes |
| `timeoutSeconds` | Time allowed for one probe |
| `successThreshold` | Successes needed to count as healthy (usually 1 for liveness) |
| `failureThreshold` | Consecutive failures before the container is marked unready or unhealthy |

## When to Use Each

**Readiness probe:** use it when the app needs time to initialize, or can temporarily be unable to serve (for example, waiting on a dependency). It stops traffic reaching unprepared containers. It may not be needed for fast-starting, stateless services that are ready immediately.

**Liveness probe:** essential when an app can **hang** while its process still runs (a frozen thread or an infinite loop). It may not be needed for short-lived processes, or when another system handles restarts.

**Together?** Yes, and it's often recommended. Readiness controls **traffic**; liveness controls **restarts**. A container can be alive but not ready.

## The Lab App

`kodekloud/webapp-delayed-start` is a Flask app built for testing probes:

- `APP_START_DELAY` sets how many seconds it takes to start.
- `/ready` and `/live` are its health endpoints.
- `/crash` makes it crash; `/freeze` makes it hang.

### Step 1: A development app (starts immediately)

```yaml
# cloudops-dev.yaml
apiVersion: v1
kind: Pod
metadata:
  name: cloudops-development-webapp
  labels:
    app: development
spec:
  containers:
  - name: development-webapp
    image: kodekloud/webapp-delayed-start
    ports:
    - containerPort: 8080
      protocol: TCP
```

```yaml
# service-dev.yaml
apiVersion: v1
kind: Service
metadata:
  name: cloudops-dev-service
  namespace: default
spec:
  ports:
  - nodePort: 30080
    port: 8080
    protocol: TCP
    targetPort: 8080
  selector:
    app: development
  type: NodePort
```

### Step 2: A production app with an 80-second start delay

```yaml
# cloudops-prod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: cloudops-production-webapp
  labels:
    app: production
spec:
  containers:
  - name: production-webapp
    image: kodekloud/webapp-delayed-start
    ports:
    - containerPort: 8080
      protocol: TCP
    env:
     - name: APP_START_DELAY
       value: "80"
```

```console
[root@client1 ahmad]# kubectl apply -f cloudops-prod.yaml
pod/cloudops-production-webapp created
[root@client1 ahmad]# kubectl port-forward pod/cloudops-production-webapp 8080:8080
[root@client1 ahmad]# curl http://localhost:8080
  <h1>Hello from cloudops-production-webapp!</h1>
```

The page only became reachable **after 80 seconds**, yet without a probe the pod showed `1/1 Running` the whole time. A Service would have sent traffic to a pod that wasn't ready.

## Readiness Probe in Action

Add a readiness probe to the production pod and raise the start delay to 180 seconds:

```yaml
    env:
     - name: APP_START_DELAY
       value: "180"
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
```

```console
[root@client1 ahmad]# kubectl replace --force -f cloudops-prod.yaml
pod/cloudops-production-webapp replaced
[root@client1 ahmad]# kubectl get po
NAME                          READY   STATUS    RESTARTS   AGE
cloudops-development-webapp   1/1     Running   0          36m
cloudops-production-webapp    0/1     Running   0          10s
```

`0/1 Running`: the container runs, but it is **not ready**, so it's kept out of the Service.

```console
[root@client1 ahmad]# curl http://localhost:8080
  <h1>Hello from cloudops-development-webapp!</h1>
[root@client1 ahmad]# curl http://localhost:8081
curl: (7) Failed to connect to localhost port 8081: Connection refused

[root@client1 ahmad]# kubectl get po
NAME                          READY   STATUS    RESTARTS   AGE
cloudops-development-webapp   1/1     Running   0          38m
cloudops-production-webapp    0/1     Running   0          3m6s
[root@client1 ahmad]# kubectl get po
NAME                          READY   STATUS    RESTARTS   AGE
cloudops-development-webapp   1/1     Running   0          38m
cloudops-production-webapp    1/1     Running   0          3m7s

[root@client1 ahmad]# curl http://localhost:8081
  <h1>Hello from cloudops-production-webapp!</h1>
```

After the delay, the readiness probe passes, the pod turns `1/1`, and it starts receiving traffic.

## Why We Need Liveness Probes

**Crash:**

```console
[root@client1 ahmad]# curl http://localhost:8081/crash
Message from cloudops-production-webapp : Mayday! Mayday! Going to crash!
[root@client1 ahmad]# kubectl get po
NAME                          READY   STATUS    RESTARTS      AGE
cloudops-development-webapp   1/1     Running   0             82m
cloudops-production-webapp    0/1     Running   1 (12s ago)   46m
[root@client1 ahmad]# curl http://localhost:8081
curl: (52) Empty reply from server
```

A crash ends the process, so the kubelet restarts the container on its own (`RESTARTS 1`).

**Freeze:**

```console
[root@client1 ahmad]# curl http://localhost:8080/freeze
[root@client1 ahmad]# curl http://localhost:8080
<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 3.2 Final//EN">
<title>500 Internal Server Error</title>
<h1>Internal Server Error</h1>
<p>The server encountered an internal error and was unable to complete your request.  Either the server is overloaded or there is an error in the application.</p>
[root@client1 ahmad]# kubectl get po
NAME                          READY   STATUS    RESTARTS        AGE
cloudops-development-webapp   1/1     Running   0               87m
cloudops-production-webapp    1/1     Running   1 (5m39s ago)   51m
```

A **frozen** app is the dangerous case: it returns errors, but the process is still running, so Kubernetes still reports `1/1 Running` with **no restart**. This is exactly what a liveness probe fixes.

## Adding Liveness Probes

```yaml
# cloudops-dev.yaml
spec:
  containers:
  - name: development-webapp
    image: kodekloud/webapp-delayed-start
    ports:
    - containerPort: 8080
      protocol: TCP
    livenessProbe:
      httpGet:
        path: /live
        port: 8080
```

```yaml
# cloudops-prod.yaml
    env:
     - name: APP_START_DELAY
       value: "120"
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
    livenessProbe:
      httpGet:
        path: /live
        port: 8080
```

```console
[root@client1 ahmad]# kubectl replace --force -f cloudops-prod.yaml
[root@client1 ahmad]# kubectl replace --force -f cloudops-dev.yaml
[root@client1 ahmad]# kubectl get po
NAME                          READY   STATUS    RESTARTS   AGE
cloudops-development-webapp   1/1     Running   0          8s
cloudops-production-webapp    0/1     Running   0          51s
[root@client1 ahmad]# kubectl get po
NAME                          READY   STATUS    RESTARTS     AGE
cloudops-development-webapp   1/1     Running   0            20s
cloudops-production-webapp    0/1     Running   1 (2s ago)   63s
```

**A new problem:** the production pod was **restarted at about 60 seconds**. The liveness probe started checking immediately, `/live` failed while the app was still starting (120 seconds), and after enough failures the kubelet killed it. It would keep restarting and never become ready.

### The fix: `initialDelaySeconds`

```yaml
    livenessProbe:
      httpGet:
        path: /live
        port: 8080
      periodSeconds: 3
      initialDelaySeconds: 130
```

```console
[root@client1 ahmad]# kubectl replace --force -f cloudops-prod.yaml
pod "cloudops-production-webapp" deleted
pod/cloudops-production-webapp replaced
[root@client1 ahmad]# kubectl get po
NAME                          READY   STATUS    RESTARTS   AGE
cloudops-development-webapp   1/1     Running   0          61m
cloudops-production-webapp    0/1     Running   0          107s
[root@client1 ahmad]# curl http://localhost:8081
curl: (52) Empty reply from server

[root@client1 ahmad]# kubectl get po
NAME                          READY   STATUS    RESTARTS   AGE
cloudops-development-webapp   1/1     Running   0          63m
cloudops-production-webapp    1/1     Running   0          3m55s
[root@client1 ahmad]# curl http://localhost:8081
  <h1>Hello from cloudops-production-webapp!</h1>
```

No restarts this time; the page is up after about 2 minutes.

> **Key lesson:** the liveness probe's `initialDelaySeconds` must be **longer than the app's start-up time** (`APP_START_DELAY`), or the probe kills the container before it ever starts. For very slow apps, a **startup probe** is the cleaner solution.
