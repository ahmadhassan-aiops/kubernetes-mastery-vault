# 12. Commands and Arguments

## Docker vs Kubernetes

| Docker (Dockerfile) | Kubernetes (pod spec) | Meaning |
|---|---|---|
| `ENTRYPOINT` | `command` | The program to run |
| `CMD` | `args` | The default arguments passed to it |

Setting `command` in a pod overrides the image's `ENTRYPOINT`; setting `args` overrides its `CMD`.

## Example 1: `sleep 10` and the CrashLoopBackOff

```yaml
# cmd-test.yaml
apiVersion: v1
kind: Pod
metadata:
  name: cloudops-pod
  namespace: default
  labels:
    app: cloudops
spec:
  containers:
  - name: ubuntu
    image: ubuntu
    command: [ "sleep" ]
    args: [ "10" ]
```

```console
[root@client1 ahmad]# kubectl apply -f cmd-test.yaml
pod/cloudops-pod created
[root@client1 ahmad]# kubectl get pods
NAME           READY   STATUS      RESTARTS      AGE
cloudops-pod   0/1     Completed   1 (15s ago)   105s
```

`describe` confirms the command and args, and shows the container exiting after exactly 10 seconds with code 0:

```console
[root@client1 ahmad]# kubectl describe po cloudops-pod
Containers:
  ubuntu:
    Image:         ubuntu
    Command:
      sleep
    Args:
      10
    State:          Terminated
      Reason:       Completed
      Exit Code:    0
      Started:      Sat, 03 May 2025 20:40:55 +0500
      Finished:     Sat, 03 May 2025 20:41:05 +0500
    Last State:     Terminated
      Reason:       Completed
      Exit Code:    0
    Ready:          False
    Restart Count:  2
Events:
  Normal   Pulling    15s (x3 over 53s)  kubelet  Pulling image "ubuntu"
  Normal   Created    13s (x3 over 51s)  kubelet  Created container: ubuntu
  Normal   Started    13s (x3 over 51s)  kubelet  Started container ubuntu
  Warning  BackOff    2s (x2 over 28s)   kubelet  Back-off restarting failed container ubuntu in pod cloudops-pod_default(...)
```

```console
[root@client1 ahmad]# kubectl get pods
NAME           READY   STATUS    RESTARTS      AGE
cloudops-pod   1/1     Running   3 (35s ago)   86s
[root@client1 ahmad]# kubectl get pods
NAME           READY   STATUS      RESTARTS      AGE
cloudops-pod   0/1     Completed   3 (54s ago)   105s
[root@client1 ahmad]# kubectl get pods
NAME           READY   STATUS             RESTARTS      AGE
cloudops-pod   0/1     CrashLoopBackOff   3 (22s ago)   111s
```

**Why the loop?** The container sleeps for 10 seconds and exits normally. A pod's default `restartPolicy` is `Always`, so Kubernetes expects it to keep running and restarts it, it completes again, and so on. The growing back-off delay shows up as `CrashLoopBackOff`.

## Changing a Running Pod: `edit` and `replace --force`

Most fields of a running pod can't be changed (only a few, such as the image):

```console
[root@client1 ahmad]# kubectl edit po cloudops-pod
error: pods "cloudops-pod" is invalid
A copy of your changes has been stored to "/tmp/kubectl-edit-4203417291.yaml"
error: Edit cancelled, no valid changes were saved.
```

Kubernetes saves your edit to a temporary file. Use it to **delete and recreate** the pod in one step (here with `args` changed to `4800`):

```console
[root@client1 ahmad]# kubectl replace --force -f /tmp/kubectl-edit-4203417291.yaml
pod "cloudops-pod" deleted
pod/cloudops-pod replaced
[root@client1 ahmad]# kubectl get po
NAME           READY   STATUS    RESTARTS   AGE
cloudops-pod   1/1     Running   0          12s
[root@client1 ahmad]# kubectl describe po cloudops-pod
    Command:
      sleep
    Args:
      4800
    State:          Running
      Started:      Sat, 03 May 2025 20:50:21 +0500
    Ready:          True
    Restart Count:  0
```

## Example 2: Passing Args from the Command Line

Everything after `--` in `kubectl run` becomes the container's **args**:

```console
[root@client1 ahmad]# kubectl run test --image kodekloud/webapp-color --dry-run=client -o yaml -- --color red > testpod.yaml
[root@client1 ahmad]# cat testpod.yaml
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: null
  labels:
    run: test
  name: test
spec:
  containers:
  - args:
    - --color
    - red
    image: kodekloud/webapp-color
    name: test
    resources: {}
  dnsPolicy: ClusterFirst
  restartPolicy: Always
status: {}

[root@client1 ahmad]# kubectl apply -f testpod.yaml
pod/test created
[root@client1 ahmad]# kubectl describe pods test
Containers:
  test:
    Image:         kodekloud/webapp-color
    Args:
      --color
      red
    State:          Running
```

Expose it as a NodePort Service:

```console
[root@client1 ahmad]# kubectl expose pod test --port 8080 --name test-service --type NodePort --dry-run=client -o yaml > test-svc.yaml
[root@client1 ahmad]# kubectl apply -f test-svc.yaml
service/test-service created
[root@client1 ahmad]# kubectl describe svc test-service
Name:                     test-service
Selector:                 run=test
Type:                     NodePort
IP:                       10.96.30.226
Port:                     <unset>  8080/TCP
TargetPort:               8080/TCP
NodePort:                 <unset>  32719/TCP
Endpoints:                10.244.1.74:8080
```

With kind, the node is a Docker container, so the NodePort isn't reachable from outside straight away. **Port-forwarding** works instead:

```console
[root@client1 ahmad]# kubectl port-forward pod/test 2222:8080
Forwarding from 127.0.0.1:2222 -> 8080
Forwarding from [::1]:2222 -> 8080
Handling connection for 2222
```

Browsing to `127.0.0.1:2222` inside the VM shows a **red** page. Changing the arg to `green` and recreating the pod turns it green:

```console
[root@client1 ahmad]# kubectl replace --force -f testpod.yaml
pod "test" deleted
pod/test replaced
[root@client1 ahmad]# kubectl port-forward pod/test 2222:8080
error: unable to forward port because pod is not running. Current status=Pending
[root@client1 ahmad]# kubectl port-forward pod/test 2222:8080
Forwarding from 127.0.0.1:2222 -> 8080
Handling connection for 2222
```

> Wait until the pod is `Running` before port-forwarding.
