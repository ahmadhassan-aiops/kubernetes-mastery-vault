# 07. Deployment Updates and Rollbacks

Deployments can **roll out** and **roll back**, which plain ReplicaSets cannot. This lets you move your application to a new version seamlessly.

| Option | What happens |
|---|---|
| **Recreate** | All existing pods are shut down, then recreated with the new version. Causes **downtime**. |
| **Rolling update** | Pods are replaced a few at a time until all run the new version. No downtime. This is the default. |
| **Rollback** | Return to an older version, for example after a compatibility problem. The opposite of a rollout. |

## The Deployment

```yaml
# rolling-deploy.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-deployment
  labels:
    app: myapp
    tier: frontend
spec:
  replicas: 5
  selector:
    matchLabels:
      app: cloudops-app
  template:
    metadata:
      name: nginx-2
      labels:
        app: cloudops-app
    spec:
      containers:
      - name: nginx-container
        image: nginx
```

```console
[root@client1 ahmad]# kubectl apply -f rolling-deploy.yaml
deployment.apps/myapp-deployment created
[root@client1 ahmad]# kubectl rollout status deploy myapp-deployment
deployment "myapp-deployment" successfully rolled out
[root@client1 ahmad]# kubectl rollout history deploy myapp-deployment
deployment.apps/myapp-deployment
REVISION  CHANGE-CAUSE
1         <none>
```

## Recording the Change Cause

`CHANGE-CAUSE` is empty unless you record it. Recreate the Deployment with `--record` (deprecated but still working):

```console
[root@client1 ahmad]# kubectl apply -f rolling-deploy.yaml --record
Flag --record has been deprecated, --record will be removed in the future
deployment.apps/myapp-deployment created
[root@client1 ahmad]# kubectl rollout history deploy myapp-deployment
deployment.apps/myapp-deployment
REVISION  CHANGE-CAUSE
1         kubectl apply --filename=rolling-deploy.yaml --record=true
```

The cause is stored as an annotation on the Deployment:

```console
[root@client1 ahmad]# kubectl describe deploy myapp-deployment
Annotations:            deployment.kubernetes.io/revision: 1
                        kubernetes.io/change-cause: kubectl apply --filename=rolling-deploy.yaml --record=true
Selector:               app=cloudops-app
Replicas:               5 desired | 5 updated | 5 total | 5 available | 0 unavailable
StrategyType:           RollingUpdate
RollingUpdateStrategy:  25% max unavailable, 25% max surge
```

> The modern alternative to `--record` is to set the annotation yourself: `kubectl annotate deploy myapp-deployment kubernetes.io/change-cause="update to 1.22"`.

## Update 1: `kubectl edit` (nginx → nginx:1.22)

```console

```

## A Broken Update (Image That Doesn't Exist)

```console
[root@client1 ahmad]# kubectl set image deploy myapp-deployment nginx-container=nginx:not-available-image --record
deployment.apps/myapp-deployment image updated
[root@client1 ahmad]# kubectl rollout status deploy myapp-deployment
Waiting for deployment "myapp-deployment" rollout to finish: 3 out of 5 new replicas have been updated...

[root@client1 ahmad]# kubectl get pods
NAME                                READY   STATUS             RESTARTS   AGE
myapp-deployment-5bc9f88f96-7f49x   0/1     ImagePullBackOff   0          50s
myapp-deployment-5bc9f88f96-n5btk   0/1     ImagePullBackOff   0          50s
myapp-deployment-5bc9f88f96-q5frf   0/1     ErrImagePull       0          50s
myapp-deployment-5cc66654f4-59dm8   1/1     Running            0          4m50s
myapp-deployment-5cc66654f4-72vfx   1/1     Running            0          4m50s
myapp-deployment-5cc66654f4-gjjv2   1/1     Running            0          4m45s
myapp-deployment-5cc66654f4-mgqr5   1/1     Running            0          4m50s
```

**4 old pods are still running.** The rolling update stops when new pods fail, so the app stays available (25% max unavailable means at most 1 of 5 pods may be down).

## Rolling Back

**Undo the last change:**

```console
[root@client1 ahmad]# kubectl rollout undo deploy myapp-deployment
deployment.apps/myapp-deployment rolled back
[root@client1 ahmad]# kubectl rollout history deploy myapp-deployment
deployment.apps/myapp-deployment
REVISION  CHANGE-CAUSE
1         kubectl apply --filename=rolling-deploy.yaml --record=true
2         kubectl edit deploy myapp-deployment --record=true
4         kubectl set image deploy myapp-deployment nginx-container=nginx:not-available-image --record=true
5         kubectl set image deploy myapp-deployment nginx-container=nginx:1.27.5 --record=true

[root@client1 ahmad]# kubectl get po,rs,deploy
NAME                                    READY   STATUS    RESTARTS   AGE
pod/myapp-deployment-5cc66654f4-59dm8   1/1     Running   0          8m14s
pod/myapp-deployment-5cc66654f4-5sbpb   1/1     Running   0          36s
pod/myapp-deployment-5cc66654f4-72vfx   1/1     Running   0          8m14s
pod/myapp-deployment-5cc66654f4-gjjv2   1/1     Running   0          8m9s
pod/myapp-deployment-5cc66654f4-mgqr5   1/1     Running   0          8m14s

NAME                                          DESIRED   CURRENT   READY   AGE
replicaset.apps/myapp-deployment-5bc9f88f96   0         0         0       4m14s
replicaset.apps/myapp-deployment-5cc66654f4   5         5         5       8m14s
replicaset.apps/myapp-deployment-658f5885b    0         0         0       16m
replicaset.apps/myapp-deployment-7864c9d495   0         0         0       34m
```

Notice that revision 3 disappeared and came back as **revision 5**: a rollback re-applies an old template as a new revision.

**Roll back to a specific revision** (revision 2, nginx:1.22):

```console
[root@client1 ahmad]# kubectl rollout undo deploy myapp-deployment --to-revision=2
deployment.apps/myapp-deployment rolled back
[root@client1 ahmad]# kubectl rollout history deploy myapp-deployment
deployment.apps/myapp-deployment
REVISION  CHANGE-CAUSE
1         kubectl apply --filename=rolling-deploy.yaml --record=true
4         kubectl set image deploy myapp-deployment nginx-container=nginx:not-available-image --record=true
5         kubectl set image deploy myapp-deployment nginx-container=nginx:1.27.5 --record=true
6         kubectl edit deploy myapp-deployment --record=true

[root@client1 ahmad]# kubectl describe deploy myapp-deployment
Annotations:            deployment.kubernetes.io/revision: 6
                        kubernetes.io/change-cause: kubectl edit deploy myapp-deployment --record=true
  Containers:
   nginx-container:
    Image:         nginx:1.22
OldReplicaSets:  myapp-deployment-7864c9d495 (0/0 replicas created), myapp-deployment-5cc66654f4 (0/0 replicas created), myapp-deployment-5bc9f88f96 (0/0 replicas created)
NewReplicaSet:   myapp-deployment-658f5885b (5/5 replicas created)
```

The original `658f5885b` ReplicaSet was reused for the rollback.

## Command Summary

| Command | Purpose |
|---|---|
| `kubectl rollout status deploy <name>` | Watch a rollout progress |
| `kubectl rollout history deploy <name>` | List revisions |
| `kubectl rollout history deploy <name> --revision=N` | Show one revision's template |
| `kubectl set image deploy <name> <container>=<image>` | Update the image |
| `kubectl edit deploy <name>` | Edit the live object |
| `kubectl rollout undo deploy <name>` | Go back one revision |
| `kubectl rollout undo deploy <name> --to-revision=N` | Go back to a specific revision |
