# 03. Security Controls and Frameworks

To keep Kubernetes secure, you apply **security controls** and organize them with trusted **security frameworks**. Together they reduce risk, enforce rules and keep you compliant with industry standards.

## Security Controls

A **security control** is a rule or mechanism that reduces risk or enforces a security policy.

| Control | What it does | Example |
|---|---|---|
| **Network Policies** | Control how pods communicate | A pod only accepts traffic on one port from a trusted source |
| **RBAC** | Grants permissions to users and groups based on their role | A user can view the cluster but not change anything |
| **Pod Security Admission** | Rules every pod must meet before it may run | Containers must not run as root or privileged |
| **Admission policies** | Custom rules on any object (OPA Gatekeeper, Kyverno, ValidatingAdmissionPolicy) | Images must come from the company registry |
| **Secrets encryption** | Protects sensitive data stored in etcd | Secrets encrypted with a KMS key |

Organizations also define their **own internal policies**, which these controls enforce.

> PodSecurityPolicy (PSP), mentioned in older material, was removed in Kubernetes 1.25. Its replacement is Pod Security Admission ([topic 10](10.%20Pod%20Security%20Standards%20and%20Admission.md)).

### Types of control

| Type | Purpose | Kubernetes example |
|---|---|---|
| **Preventive** | Stop an incident before it happens | RBAC, admission control, Network Policies |
| **Detective** | Notice an incident while or after it happens | Audit logs, Falco runtime alerts |
| **Corrective** | Limit damage and recover | Backups, automated rollback, revoking credentials |

## Security Frameworks

A **security framework** is a structured set of guidelines that helps you choose, organize and apply controls.

| Framework | From | What it gives you | Example use |
|---|---|---|---|
| **CIS Kubernetes Benchmark** | Center for Internet Security | A detailed checklist for configuring Kubernetes components securely | Make sure the API server requires authentication ([CKS topic 03](../04-CKS/03.%20CIS%20Benchmark%20with%20kube-bench.md)) |
| **NIST** (SP 800-190, Cybersecurity Framework) | US National Institute of Standards and Technology | Risk management and control guidance for containers and systems | Build a risk management plan for your clusters |
| **NSA/CISA Kubernetes Hardening Guide** | US government agencies | Practical hardening recommendations | Harden pods, networks and authentication |
| **MITRE ATT&CK for Containers** | MITRE | A catalogue of attacker techniques | Map your defences to real attack paths |
| **Pod Security Standards** | Kubernetes project | Three levels of pod hardening | Enforce `restricted` on production namespaces |

**Open Policy Agent (OPA)** is not a framework itself but a **policy engine** for writing and enforcing custom rules, for example blocking privileged containers. See [CKS topic 16](../04-CKS/16.%20OPA%20Gatekeeper%20Policies.md).

## Using Them Together

- **CIS:** follow the benchmark checklist, check with kube-bench, fix what fails.
- **NIST:** build a security plan that matches your organization's risk.
- **OPA / admission policies:** encode your own rules so they are enforced automatically.

## Continuous Monitoring and Compliance

Security isn't a one-time job.

- **Security audits:** regularly review the cluster for weaknesses and policy violations.
- **Automated compliance checks:** tools that continuously compare your setup against CIS or NIST.
- **Logging and alerting:** collect logs and alert on unusual behaviour such as unauthorized access or broken policies ([topic 12](12.%20Audit%20Logging.md)).
