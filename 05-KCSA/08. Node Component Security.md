# 08. Node Component Security

Every worker node runs three Kubernetes components: the **kubelet**, a **container runtime** and **kube-proxy**. A compromised node exposes every pod on it, so each component must be locked down.

---

## 1. The Kubelet

The **kubelet** is the node agent. It runs on every node and:

- receives pod specs from the API server and makes sure their containers are running
- runs **liveness, readiness and startup probes**
- **registers the node** and reports its capacity and status
- enforces resource limits and QoS
- talks to the container runtime through the **CRI**

### Why it's sensitive

The kubelet exposes an HTTPS API on **port 10250** that can list pods, read logs and **execute commands in containers**. If it accepts anonymous requests, anyone who can reach the port can take over the node's workloads.

### Securing it

Settings in the kubelet config file (`/var/lib/kubelet/config.yaml`):

```yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
authentication:
  anonymous:
    enabled: false              # reject unauthenticated requests
  webhook:
    enabled: true               # validate tokens with the API server
  x509:
    clientCAFile: /etc/kubernetes/pki/ca.crt
authorization:
  mode: Webhook                 # ask the API server (RBAC) whether a request is allowed
readOnlyPort: 0                 # disable the old unauthenticated read-only port 10255
rotateCertificates: true        # rotate the kubelet's client certificate
serverTLSBootstrap: true        # request a signed serving certificate
protectKernelDefaults: true
```

Also:

- **NodeRestriction** admission plugin on the API server, together with the **Node authorizer**: a kubelet can only modify its own Node object and the pods bound to it.
- **Firewall port 10250** so only the control plane can reach it.
- **Keep the node OS, kubelet and runtime patched** ([CKS topic 10](../04-CKS/10.%20Upgrading%20Kubernetes%20Frequently.md)).
- Monitor kubelet logs (`journalctl -u kubelet`). Actions taken through the API server appear in the API server's audit log.

## 2. The Container Runtime

The **container runtime** pulls images, starts and stops containers, and reports their status to the kubelet. Kubernetes talks to it through the **Container Runtime Interface (CRI)**, so runtimes are interchangeable.

| Runtime | Notes |
|---|---|
| **containerd** | Lightweight and the most common default |
| **CRI-O** | Built specifically for Kubernetes, OCI-compliant |
| Docker Engine | No longer used directly since Kubernetes 1.24 removed dockershim; it needs the `cri-dockerd` adapter. Images built with Docker still run everywhere. |

Under the CRI runtime, a low-level **OCI runtime** such as `runc` actually creates the container using Linux **namespaces** (isolation) and **cgroups** (resource limits).

### Securing it

1. **Minimal, patched base images** to reduce the attack surface.
2. **Scan images** before deploying them (Trivy, Grype).
3. **Run as non-root:** `USER` in the Dockerfile and `runAsNonRoot` in the pod.
   ```dockerfile
   FROM nginxinc/nginx-unprivileged:1.27
   USER 101
   ```
4. **Use kernel security features:** seccomp, AppArmor or SELinux ([CKS topics 13 and 14](../04-CKS/13.%20Kernel%20Hardening%20with%20AppArmor.md)).
5. **Protect the runtime socket** (`/run/containerd/containerd.sock`): anyone who can write to it controls every container on the node. Never mount it into pods.

### Runtime sandboxes

For untrusted workloads, a **sandboxed runtime** adds a layer between the container and the host kernel:

| Sandbox | How it isolates |
|---|---|
| **gVisor** (`runsc`) | A user-space kernel intercepts the container's system calls |
| **Kata Containers** | Each pod runs inside a lightweight virtual machine with its own kernel |

Pods choose one through a **RuntimeClass**:

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc          # must match the runtime handler configured in containerd
---
apiVersion: v1
kind: Pod
metadata:
  name: untrusted
spec:
  runtimeClassName: gvisor
  containers:
  - name: app
    image: nginx
```

The trade-off is some performance overhead and less compatibility for unusual system calls.

## 3. kube-proxy

**kube-proxy** runs on every node and implements **Services**: it watches Services and EndpointSlices through the API server and programs rules so traffic to a Service IP reaches one of its pods (load balancing across replicas).

| Mode | Notes |
|---|---|
| **iptables** | The default on Linux |
| **IPVS** | Kernel load balancer, scales better with many Services |
| **nftables** | Newer mode replacing iptables |
| userspace | Old and slow; removed in Kubernetes 1.26 |

> kube-proxy does **not** enforce Network Policies; the **CNI plugin** does (Calico, Cilium). Some CNIs (Cilium) can replace kube-proxy entirely.

### Securing it

- It runs with a kubeconfig whose identity has the minimal `system:node-proxier` role.
- It talks to the API server over **TLS**; protect its kubeconfig (`/var/lib/kube-proxy/kubeconfig.conf`).
- Bind its metrics port (10249) to localhost unless you scrape it from elsewhere.
- Restrict NodePort exposure with firewalls and avoid NodePorts for sensitive Services.
- Monitor it with Prometheus metrics and its logs.
