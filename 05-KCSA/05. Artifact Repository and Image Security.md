# 05. Artifact Repository and Image Security

## Key Terms

- An **artifact repository** is a server that stores and manages build outputs: binaries, libraries and **container images**. In CI/CD pipelines it's the hand-off point between build and deploy, so its security directly affects what runs in production.
- **Image security** is the set of practices that keep container images free from vulnerabilities, unauthorized access and tampering, from build to runtime.

This is part of the **supply chain**: everything that goes into the software you run.

```text
source code → build → image → registry → admission → cluster
     │          │       │        │           │          │
   SAST      pinned   scan,    access      verify     runtime
   review    deps     sign     control    signature   monitor
```

## Securing Repositories and Images

### 1. Use private repositories

- **Examples:** JFrog Artifactory, Sonatype Nexus, Harbor, or private registries on Docker Hub, GitHub Packages, GitLab Container Registry, Amazon ECR.
- **Benefit:** only trusted parties can push or pull, reducing the risk of tampering.

### 2. Enforce strong access control

- **Example:** RBAC in the registry so only the CI system can push to production repositories, and clusters can only pull.
- **Benefit:** stops unauthorized changes to artifacts.

### 3. Scan images for vulnerabilities

- **Tools:** Trivy, Grype, Clair, Anchore.
- **Where:** in the CI pipeline before pushing, in the registry on push, and again on a schedule (new CVEs appear for old images).

```bash
trivy image nginx:1.27            # list known vulnerabilities in an image
trivy image --severity HIGH,CRITICAL --exit-code 1 myapp:1.0   # fail the build on serious findings
```

### 4. Use immutable tags and signed images

- **Immutable tags:** once a tag such as `myapp:1.4.2` is pushed, it must never be overwritten. Better still, deploy by **digest** (`myapp@sha256:...`), which always identifies exactly the same image. Avoid `latest` in production.
- **Signing:** sign images with **Sigstore cosign** or **Notary v2 (Notation)**; Docker Content Trust is the older approach.
- **Benefit:** proves the image is the one your pipeline built and hasn't been changed.

```bash
cosign sign registry.example.com/myapp@sha256:...
cosign verify --key cosign.pub registry.example.com/myapp@sha256:...
```

### 5. Verify at admission

Make the cluster check images before running them: an admission policy (Kyverno, OPA Gatekeeper, Sigstore policy-controller) can allow only signed images from approved registries. See [CKS topic 16](../04-CKS/16.%20OPA%20Gatekeeper%20Policies.md) for a registry allow-list.

### 6. Keep images updated

- **Tools:** Renovate or Dependabot open pull requests when base images and dependencies have updates.
- **Benefit:** fewer vulnerabilities from outdated components.

### 7. Keep images minimal

Use small base images (distroless, Alpine, Chainguard, scratch) and multi-stage builds so compilers and shells don't end up in production images. Fewer packages mean fewer vulnerabilities.

### 8. Generate an SBOM

A **Software Bill of Materials** lists every component in an image (Syft, `trivy image --format spdx`). When a new vulnerability is announced, you can instantly see which images contain the affected component.

### 9. Monitor running containers

- **Tools:** Falco, Sysdig, Aqua.
- **Benefit:** detects unexpected behaviour in real time, such as a shell spawned in a container or an unexpected outbound connection.
