# 11. Authentication, Authorization and Secrets

Think of the cluster as a walled city. **Authentication** is the guard at the gate checking identity. **Authorization** decides where each visitor may go inside. **Secrets** are the treasures in the vault, which both must protect.

---

## 1. Authentication: Who Are You?

Authentication verifies the identity of every user and component calling the API server.

### Two kinds of identity

| Kind | Managed by | Example |
|---|---|---|
| **Users** (humans) | **Outside** Kubernetes: certificates, an identity provider | `ahmad`, `dev@example.com` |
| **Service accounts** (workloads) | **Inside** Kubernetes as API objects | `system:serviceaccount:prod:api` |

Kubernetes has no User object; a user is whoever presents valid credentials.

### Methods

| Method | How it works | Notes |
|---|---|---|
| **Client certificates** | A certificate signed by the cluster CA; CN = user, O = groups | Strong, but can't be revoked: keep lifetimes short |
| **Bearer tokens** | A token in the `Authorization` header | ServiceAccount tokens are **short-lived and bound** to a pod since v1.22 |
| **OpenID Connect (OIDC)** | Users log in at an external identity provider (Entra ID, Okta, Google, Keycloak) built on OAuth 2.0, which issues a signed ID token | Best for teams: MFA, groups and central revocation |
| **Webhook token authentication** | The API server asks an external service to validate the token | Used by some managed platforms |
| **Authenticating proxy** | A proxy authenticates the user and passes headers | Needs strict trust between proxy and API server |
| Static token file | A CSV of tokens read at startup | Avoid: long-lived, needs restarts to change |

Requests that match no method are **anonymous** (`system:anonymous`) if anonymous auth is enabled.

### Best practices

- Prefer **OIDC** for people and **short-lived ServiceAccount tokens** for workloads.
- Avoid static, long-lived tokens.
- **Rotate credentials** regularly and revoke compromised ones promptly.
- Use **TLS** for all API traffic and keep keys secure.
- Turn on **audit logging** to record authentication events.

Reference: https://kubernetes.io/docs/reference/access-authn-authz/authentication/

## 2. Authorization: What May You Do?

After authentication, the API server asks its **authorizers**, in the order of `--authorization-mode`, whether the request is allowed. The first one to allow or deny decides; if none allows, the request is denied.

### Why it matters

- **Least privilege:** each user gets only what they need, like a delivery driver allowed in loading zones but not the power station.
- **Smaller blast radius:** a stolen credential can only do what its role allows.
- **Stronger overall posture:** critical resources are protected even from authenticated users.

### Authorization modes

| Mode | Purpose |
|---|---|
| **RBAC** | Role-based permissions: the standard choice |
| **Node** | Restricts kubelets to the objects related to their own node |
| **Webhook** | Ask an external service; secure it with mTLS and high availability |
| ABAC | Attribute-based policies from a file; legacy and rarely used |
| AlwaysAllow / AlwaysDeny | Testing only; never `AlwaysAllow` in a real cluster |

The common production setting is `--authorization-mode=Node,RBAC`.

### RBAC objects

| Object | Scope | Purpose |
|---|---|---|
| **Role** | Namespace | Permissions, e.g. "developer" or "view-only" |
| **ClusterRole** | Cluster | Cluster-wide permissions, or for cluster-scoped resources |
| **RoleBinding** | Namespace | Gives a Role or ClusterRole to subjects in one namespace |
| **ClusterRoleBinding** | Cluster | Gives a ClusterRole everywhere |

Subjects are **users**, **groups** or **service accounts**. Built-in ClusterRoles cover common needs: `view`, `edit`, `admin`, `cluster-admin`.

### Checking access

```bash
kubectl auth can-i create deployments -n prod --as dev
kubectl auth can-i --list --as system:serviceaccount:prod:api -n prod
```

Behind the scenes these use **SubjectAccessReview**, the API for one-off authorization checks.

### Best practices

- **Least privilege**, starting restrictive and adding as needed.
- Use **predefined roles** where they fit.
- Avoid `cluster-admin` and wildcards (`*`).
- Watch the dangerous permissions: `escalate`, `bind`, `impersonate`, `create pods`, `get secrets`, `create serviceaccounts/token`.
- **Review regularly**, manage RBAC as code, and monitor denied requests in the audit log.

## 3. Secrets: Protecting Sensitive Data

A **Secret** stores sensitive data such as passwords, API keys, tokens and certificates, keeping it out of images and pod specs.

> Storing a password in a container image is like leaving the crown jewels in the hallway: anyone who gets the image has the key.

### Secret types

| Type | Use |
|---|---|
| `Opaque` | Arbitrary key-value data (the default) |
| `kubernetes.io/dockerconfigjson` | Registry credentials for pulling private images |
| `kubernetes.io/tls` | A TLS certificate and key |
| `kubernetes.io/basic-auth` | Username and password |
| `kubernetes.io/ssh-auth` | SSH private key |
| `kubernetes.io/service-account-token` | Long-lived ServiceAccount token (created only on request since v1.24) |

### How they're used

1. **Created** with kubectl or a manifest.
2. **Consumed** by pods as **environment variables** or **mounted files**. Mounted files are preferred: they update when the Secret changes and don't leak into process listings or crash dumps.
3. **Protected** by RBAC: only the pods and people that need a Secret can read it.

### The most important fact

**Secret values are only base64-encoded, not encrypted.** Anyone who can read the Secret object, or the etcd data, can decode it:

```bash
kubectl get secret db -o jsonpath='{.data.password}' | base64 -d
```

### Best practices

1. **Encrypt at rest** in etcd with an `EncryptionConfiguration`, ideally with a **KMS provider** ([topic 07](07.%20Control%20Plane%20Component%20Security.md)).
2. **Limit access with RBAC.** Note that anyone who can **create pods** in a namespace can mount any Secret in it.
3. **Audit** access to Secrets.
4. **Rotate** regularly, and update applications without downtime.
5. **External managers** for stronger guarantees: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, via the External Secrets Operator or the Secrets Store CSI Driver.
6. Never commit Secret manifests to Git unencrypted; use Sealed Secrets or SOPS.
7. Use **ConfigMaps** only for non-sensitive configuration.
