# 13. The Kubernetes Threat Model

A **threat model** asks: *what could go wrong, how would an attacker do it, and what stops them?* This topic covers the KCSA threat model domain: trust boundaries and data flow, then the six main threat categories.

---

## 1. Trust Boundaries and Data Flow

A **trust boundary** is a line where the level of trust changes, for example between the internet and the cluster, or between one tenant's namespace and another's. **Data flow** is how data moves across those lines. Every crossing is a place to authenticate, authorize, encrypt and log.

```text
 Internet ──┤ Ingress/LB ├── Pods (namespace A) ──┤ Network Policy ├── Pods (namespace B)
                                  │
                       ┤ ServiceAccount token ├
                                  ▼
 Users/CI ──┤ authn · authz · admission ├── kube-apiserver ──┤ mTLS ├── etcd
                                  ▲
                         kubelet (node boundary)
                                  │
                   container ──┤ kernel: namespaces, seccomp, AppArmor ├── host
```

### Main boundaries

| Boundary | Between | Controls |
|---|---|---|
| **External to cluster** | Internet and Ingress or Services | TLS, WAF, firewalls, rate limits |
| **Client to control plane** | Users and CI, and the API server | Authentication, RBAC, admission, audit |
| **Control plane to etcd** | API server and etcd | mTLS, network isolation, encryption at rest |
| **Control plane to nodes** | API server and kubelets | TLS, Node authorizer, NodeRestriction |
| **Pod to pod** | Workloads, namespaces, tenants | Network Policies, mTLS, namespaces |
| **Container to host** | A container and its node | Non-root, seccomp, AppArmor, PSA, sandboxes |

### Threats at the boundaries

- Unauthorized access to the API server or etcd
- Interception of data between components
- A compromised pod or node used as an entry point

### Best practices

- Define clear security zones (for example, a DMZ for internet-facing workloads) with namespaces and Network Policies.
- Encrypt everything in transit; use mTLS between components and services.
- Strict authentication and least-privilege RBAC for sensitive components.
- Monitor data flows and audit access.
- Run regular security assessments and penetration tests.

## 2. Persistence

**Persistence** means an attacker keeps access after the initial break-in, surviving pod restarts, redeployments or even fixes to the original vulnerability.

### How attackers persist

- Creating a **DaemonSet**, CronJob or static pod that keeps launching their container
- Adding a **ServiceAccount, RoleBinding or certificate** for themselves
- Planting a **mutating admission webhook** that injects their code into new pods
- Writing to a **hostPath** or persistent volume that survives restarts
- Pushing a **backdoored image** to the registry

(Persistent storage, the PV and PVC mechanism used legitimately for stateful apps, is covered in [topic 09](09.%20Networking%2C%20Storage%20and%20Client%20Security.md); here persistence is the attacker's goal.)

### Defences

- Least-privilege RBAC: few identities may create workloads, bindings or webhooks.
- **Audit logs** with alerts on new ClusterRoleBindings, webhooks, DaemonSets and CSRs.
- Block `hostPath` and static pod paths; read-only root filesystems.
- Immutable, signed images and admission checks on image sources.
- Encrypted storage, regular backups and tested recovery.
- GitOps: compare the live cluster with Git and investigate drift.

## 3. Denial of Service (DoS)

A **DoS** attack makes the cluster or an application unavailable by exhausting resources: CPU, memory, disk, PIDs, network or the API server itself.

### Defences

| Control | What it prevents |
|---|---|
| **ResourceQuotas** | One namespace consuming the whole cluster |
| **Requests and limits** (and LimitRanges for defaults) | One container starving a node |
| **PID limits** | Fork bombs |
| **Network Policies** | Floods between workloads; isolate critical services |
| **Horizontal Pod Autoscaler** | Absorbs genuine load spikes (it can also amplify costs under attack, so set `maxReplicas`) |
| **PodDisruptionBudgets** | Too many replicas taken down during voluntary disruptions |
| **Rate limiting** | Excess requests, at the Ingress controller, the application, and the API server (API Priority and Fairness) |
| **Monitoring and alerting** | Slow detection; Prometheus and Grafana alerts on resource anomalies |

## 4. Malicious Code Execution and Compromised Applications

Attackers exploit a vulnerable application or a poisoned image to **run their own code** inside a container, then try to spread to other pods, the node or the cloud account.

### Defences

1. **Minimal, trusted, regularly updated images** from known sources ([topic 05](05.%20Artifact%20Repository%20and%20Image%20Security.md)).
2. **Scan images** in CI and in the registry (Trivy, Grype, Clair).
3. **Security contexts:** non-root, no privilege escalation, read-only filesystem, dropped capabilities.
4. **Runtime security tools:** Falco, Sysdig or Aqua detect unexpected behaviour such as a shell spawned in a container, crypto-mining or writes to `/etc`.
5. **Network Policies and segmentation** contain a compromised application.
6. **Audit logging and monitoring** to detect the follow-up actions.
7. **Sandboxed runtimes** (gVisor, Kata) for untrusted code.

## 5. Attacker on the Network

An attacker with network access (inside the cluster network, on the node network, or between client and cluster) can **eavesdrop**, **tamper with traffic**, **impersonate services** or **reach exposed endpoints** such as an unauthenticated kubelet or etcd.

### Defences

- **Network Policies:** default-deny, with explicit allows for ingress and egress.
- **Encrypt in transit:** TLS for every Kubernetes component, certificates from a trusted CA, **mTLS** between services.
- **Intrusion detection:** Falco and network IDS, with alerts.
- **Firewalls and access controls:** restrict the API server, kubelet (10250) and etcd (2379-2380) ports to the hosts that need them.
- **RBAC** so stolen network access doesn't come with broad permissions.
- Review and update policies as threats evolve.

---

## 6. Access to Sensitive Data

Sensitive data includes Secrets, credentials, certificates, configuration and application data. Exposure can compromise both the applications and the cluster.

### Where it leaks

- Secrets readable by too many users or service accounts
- Credentials placed in ConfigMaps, environment variables, images or Git
- Unencrypted etcd data, backups or volumes
- The cloud instance metadata service handing out node credentials
- Logs that capture secret values

### Defences

1. **Secrets, not ConfigMaps**, for anything sensitive; mount them as files.
2. **RBAC** restricting `get`/`list`/`watch` on Secrets to the minimum.
3. **Encrypt at rest** (KMS provider) and **in transit** (TLS).
4. **Audit logging** on Secret access, at `Metadata` level ([topic 12](12.%20Audit%20Logging.md)).
5. **Rotate** Secrets and credentials regularly.
6. Block pod access to the metadata service.

---

## 7. Privilege Escalation

**Privilege escalation** is when an attacker with limited access gains more: from a pod to the node, from a namespace to the cluster, or from the cluster to the cloud account.

### Common paths

| Path | Example |
|---|---|
| **Privileged or root containers** | `privileged: true`, host namespaces or `hostPath` mounts let a container take over the node |
| **Dangerous capabilities** | `CAP_SYS_ADMIN` and similar |
| **Over-broad RBAC** | `create pods` (to mount any Secret or run privileged), `escalate`, `bind`, `impersonate`, wildcards |
| **Stolen ServiceAccount tokens** | Auto-mounted tokens with too many permissions |
| **Node credentials** | A kubelet credential used to read Secrets for pods on other nodes (prevented by the Node authorizer and NodeRestriction) |

### Defences

1. **Security contexts:** non-root, `allowPrivilegeEscalation: false`, drop all capabilities, read-only filesystem.
2. **Least-privilege RBAC**, reviewed regularly.
3. **Pod Security Admission** at `baseline` or `restricted` (the replacement for PodSecurityPolicy) ([topic 10](10.%20Pod%20Security%20Standards%20and%20Admission.md)).
4. **Admission controllers:** `NodeRestriction`, plus policy engines (Gatekeeper, Kyverno) or `ImagePolicyWebhook` to deny insecure configurations.
5. **Disable token auto-mounting** where it isn't needed.
6. **Monitor and audit** for unusual permission use.
