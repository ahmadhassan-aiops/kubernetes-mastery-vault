# 09. Networking, Storage and Client Security

Three more parts of the cluster that need protecting: the **pod and container networking**, the **storage** data lives on, and the **clients** people use to reach the cluster. The pod itself, the unit everything runs in, comes first.

---

## 1. Pod Security Basics

A **Pod** is the smallest Kubernetes object: one or more containers that share a network identity (one IP, talk over `localhost`) and storage, plus options for how they run.

- **Lifecycle phases:** Pending, Running, Succeeded, Failed, Unknown.
- **Pod templates** inside Deployments, StatefulSets and DaemonSets create pods.
- **Labels and selectors** group pods, and are what Services, Network Policies and controllers use to target them.

### Security best practices for pods

| Practice | How |
|---|---|
| **Security contexts** | Non-root users, no privilege escalation, read-only root filesystem, dropped capabilities |
| **Network Policies** | Only intended traffic in and out |
| **Resource requests and limits** | Prevent a pod exhausting a node |
| **Secrets** | Never hard-code credentials in the pod spec or image |
| **Updated images** | Minimal, scanned, regularly rebuilt |

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000                  # pod-level only: group ownership for volumes
  containers:
  - name: nginx
    image: nginxinc/nginx-unprivileged:1.27
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
```

## 2. Container Networking

Kubernetes uses a **flat network model**:

- every pod gets its **own IP address**
- every pod can reach every other pod, on any node, **without NAT**
- agents on a node can reach all pods on that node

A **CNI plugin** (Container Network Interface) implements this: Flannel, Calico, Cilium, Weave Net and others.

### The four communication problems

| Problem | Solved by |
|---|---|
| **Container to container** in a pod | The shared network namespace: `localhost` |
| **Pod to pod** across nodes | The CNI plugin: routing or an **overlay network** (VXLAN, Geneve) laid over the physical network |
| **Pod to Service** | Services give a stable IP and DNS name; kube-proxy load-balances to pods |
| **External to Service** | NodePort, LoadBalancer, Ingress or Gateway API |

> **`hostNetwork: true`** makes a pod use the **node's** network namespace instead of its own. It removes network isolation and should be reserved for system components.

### Security risks

- **Default allow:** without policies, any pod can reach any other, including databases and the cloud metadata service.
- **Plain-text traffic:** pod-to-pod traffic isn't encrypted by default.
- **Exposure:** Services published more widely than intended.

### Best practices

1. **Network Policies:** default-deny in every namespace, then allow specific flows (needs an enforcing CNI).
   ```yaml
   apiVersion: networking.k8s.io/v1
   kind: NetworkPolicy
   metadata:
     name: default-deny
     namespace: default
   spec:
     podSelector: {}
     policyTypes: ["Ingress", "Egress"]
   ```
   Hands-on: [CKS topic 02](../04-CKS/02.%20Network%20Policies%20and%20Protecting%20Node%20Metadata.md).
2. **Encrypt traffic:** **mutual TLS (mTLS)** through a service mesh (Istio, Linkerd), or CNI-level encryption (WireGuard in Calico or Cilium). With mTLS, both sides present certificates, so traffic is encrypted **and** each service proves its identity.
3. **Monitor traffic:** CNI and mesh metrics in Prometheus and Grafana; flow visibility tools such as Cilium Hubble.
4. **Limit exposure:** use Ingress with TLS instead of many NodePorts, and firewalls around the cluster.

## 3. Storage

Pods are ephemeral; **persistent storage** keeps data across restarts, rescheduling and scaling.

| Concept | Meaning |
|---|---|
| **Ephemeral storage** | Tied to the pod's life (`emptyDir`, container filesystem); gone when the pod is deleted |
| **PersistentVolume (PV)** | A piece of storage provisioned by an admin or dynamically; a cluster-scoped resource |
| **PersistentVolumeClaim (PVC)** | A user's request for storage, bound to a PV |
| **StorageClass** | Describes a type of storage and provisions PVs dynamically |
| **Access modes** | `ReadWriteOnce` (one node), `ReadOnlyMany`, `ReadWriteMany`, `ReadWriteOncePod` (one pod) |

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: encrypted-gp3
provisioner: ebs.csi.aws.com       # CSI driver (the old in-tree kubernetes.io/aws-ebs is removed)
parameters:
  type: gp3
  encrypted: "true"                # encryption at rest on the storage backend
reclaimPolicy: Retain              # keep the data when the claim is deleted
```

### Security risks

- **hostPath volumes** give a pod access to the node's filesystem, a classic container escape.
- Unencrypted disks and snapshots.
- Anyone who can create pods in a namespace can mount any PVC in it.
- Data left behind on reused volumes.

### Best practices

1. **Secure, encrypted backends**: encryption at rest on the storage system or cloud disks.
2. **Encrypt in transit** for network storage (NFS over TLS, iSCSI with CHAP and IPsec).
3. **RBAC:** limit who can create or delete PVs, PVCs and StorageClasses; PVs are cluster-wide, so only admins should manage them.
   ```yaml
   apiVersion: rbac.authorization.k8s.io/v1
   kind: Role
   metadata:
     namespace: team-a
     name: claim-manager
   rules:
   - apiGroups: [""]
     resources: ["persistentvolumeclaims"]
     verbs: ["get", "list", "create", "delete"]
   ```
4. **Block hostPath** with Pod Security Admission (`baseline` already does).
5. **Back up and test restores** (Velero, CSI snapshots).
6. **Monitor usage** to catch exhaustion or unusual access.

Hands-on with volumes: [CKAD topics 28 and 29](../02-CKAD/29.%20Persistent%20Volumes%20and%20Claims.md).

## 4. Client Security

Clients (kubectl, CI/CD systems, dashboards, custom apps) reach the cluster through the API. A well-fortified cluster with unlocked gates is still open: client credentials are often the easiest way in.

### Authentication methods for clients

| Method | Strength |
|---|---|
| **Client certificates** | Strong; like presenting a trusted ID card signed by the cluster CA. Can't be revoked, so keep them short-lived. |
| **OIDC tokens** | Strong; users log in with the company identity provider, with MFA and central revocation |
| **Short-lived tokens** | Good; ServiceAccount tokens from the TokenRequest API, like a temporary visitor pass |
| Static tokens file | Weak; long-lived and only changed by restarting the API server |
| Basic authentication | Removed from Kubernetes in v1.19 |

### Best practices

1. **Strong authentication:** OIDC for people, short-lived tokens for automation.
2. **RBAC with least privilege** for every user and pipeline.
3. **TLS everywhere:** the kubeconfig must include the cluster CA (`certificate-authority-data`) so the client verifies the server. Never use `insecure-skip-tls-verify: true`.
4. **Protect kubeconfig files:** they contain credentials.
   ```bash
   chmod 600 ~/.kube/config
   export KUBECONFIG=~/.kube/prod-config     # pick the file explicitly per environment
   ```
   Don't commit them to Git or share them in chat; prefer credential plugins (`exec`) that fetch short-lived tokens instead of embedding secrets.
5. **Audit and monitor** client access through the API server audit log.

A kubeconfig using a client certificate:

```yaml
apiVersion: v1
kind: Config
clusters:
- name: kubernetes
  cluster:
    certificate-authority: /path/to/ca.crt
    server: https://kubernetes.example.com:6443
users:
- name: dev
  user:
    client-certificate: /path/to/dev.crt
    client-key: /path/to/dev.key
contexts:
- name: dev@kubernetes
  context:
    cluster: kubernetes
    user: dev
current-context: dev@kubernetes
```
