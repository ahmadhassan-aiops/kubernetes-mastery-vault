# 07. Control Plane Component Security

The control plane makes every decision in the cluster. If an attacker controls it, they control everything. This topic covers the four control-plane components and how each is secured.

```text
                      ┌───────────────────────────┐
 users, kubectl ────► │      kube-apiserver       │ ◄──── kubelets on nodes
                      └──┬──────────┬──────────┬──┘
                         │ TLS      │ TLS      │ TLS (mTLS)
             ┌───────────┘          │          └───────────┐
             ▼                      ▼                      ▼
   kube-controller-manager    kube-scheduler              etcd
```

Only the **API server** talks to etcd. Every other component, and every user, goes through the API server.

---

## 1. The API Server

The **kube-apiserver** exposes the Kubernetes API. Every operation (deploying an application, scaling a workload, reading a Secret) is an API request.

Every request passes through:

| Stage | Question | Mechanisms |
|---|---|---|
| **Authentication** | Who are you? | Client certificates, tokens, OIDC |
| **Authorization** | Are you allowed? | RBAC (least privilege), Node authorizer, webhooks |
| **Admission control** | Is this object acceptable? | PodSecurity, ResourceQuota, LimitRanger, NodeRestriction, policy webhooks |

Plus:

- **Encryption:** TLS for all traffic; encryption at rest for Secrets.
- **Audit logging:** keep it enabled ([topic 12](12.%20Audit%20Logging.md)).

### Key flags (kubeadm: `/etc/kubernetes/manifests/kube-apiserver.yaml`)

```yaml
- --anonymous-auth=false                       # see the note in CKS topic 07
- --authorization-mode=Node,RBAC
- --enable-admission-plugins=NodeRestriction
- --client-ca-file=/etc/kubernetes/pki/ca.crt
- --tls-cert-file=/etc/kubernetes/pki/apiserver.crt
- --tls-private-key-file=/etc/kubernetes/pki/apiserver.key
- --encryption-provider-config=/etc/kubernetes/enc/encryption-config.yaml
- --audit-policy-file=/etc/kubernetes/audit-policy.yaml
- --audit-log-path=/var/log/kubernetes/audit.log
```

Hands-on: [CKS topic 07](../04-CKS/07.%20Restricting%20Access%20to%20the%20API%20Server.md).

### Client certificates

A user certificate is signed by the cluster CA. The **CN** becomes the username and the **O** fields become groups:

```bash
openssl genrsa -out dev.key 2048
openssl req -new -key dev.key -out dev.csr -subj "/CN=dev/O=developers"
openssl x509 -req -in dev.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out dev.crt -days 365
```

> Never issue certificates with `O=system:masters` to people: that group bypasses RBAC entirely and can't be restricted or revoked.

## 2. The Controller Manager

The **kube-controller-manager** runs the controllers that keep the cluster in its desired state: the Node, Job, EndpointSlice, ServiceAccount, ReplicaSet and PersistentVolume controllers, among others.

Each controller follows the same loop:

1. **Monitor** the cluster state through the API server.
2. **Compare** it with the desired state (the specs you applied).
3. **Reconcile:** take action to close any gap.

### Why it's sensitive

It holds the **service account signing key** (`--service-account-private-key-file`) and, with `--use-service-account-credentials`, runs each controller with its own limited identity.

### Securing it

- **RBAC:** controllers use the built-in `system:kube-controller-manager` and `system:controller:*` roles; don't widen them.
- **TLS:** it talks to the API server over TLS with its own kubeconfig; rotate those certificates.
- **Bind its secure port to localhost** (`--bind-address=127.0.0.1`), and protect its kubeconfig and key files on disk.
- **Monitor** its health endpoint and logs. (Audit logs are written by the API server, which records the controller manager's requests.)

## 3. The Scheduler

The **kube-scheduler** watches for new pods with no node assigned and picks a node for each.

### How it decides

- **Filtering** (formerly "predicates"): remove nodes that can't run the pod, for example with insufficient CPU or memory, or a taint the pod doesn't tolerate.
- **Scoring** (formerly "priorities"): rank the remaining nodes and pick the best.

Inputs include resource requests and limits, **taints and tolerations**, **node and pod affinity and anti-affinity**, data locality and hardware constraints.

### Securing it

- **RBAC:** it runs as `system:kube-scheduler`; don't widen that role.
- **TLS** to the API server; `--bind-address=127.0.0.1` for its own port.
- **Use scheduling for security:** taints, tolerations and affinity keep critical pods on trusted nodes and untrusted pods away from them.

Its behaviour is configured with a `KubeSchedulerConfiguration` (`kubescheduler.config.k8s.io/v1`) passed with `--config`:

```yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
- schedulerName: default-scheduler
  plugins:
    score:
      enabled:
      - name: NodeResourcesBalancedAllocation
      - name: ImageLocality
```

## 4. etcd

**etcd** is a distributed key-value store that holds **all cluster data**: pod specs, Services, nodes, Secrets, the desired and actual state. It is the cluster's single source of truth, using the **Raft** consensus algorithm across members for high availability.

Anyone with direct etcd access can read every Secret and change anything, bypassing RBAC and admission entirely.

### Securing it

| Control | How |
|---|---|
| **Mutual TLS** | `--cert-file`, `--key-file`, `--trusted-ca-file`, `--client-cert-auth=true` for clients; the `--peer-*` equivalents between members |
| **Restrict network access** | Only the API servers may reach port 2379; only etcd members may reach 2380 |
| **Encrypt Secrets at rest** | Configured on the **API server**, not etcd (below) |
| **Encrypt the disk** | Protects the data files and snapshots |
| **Back up regularly** | `etcdctl snapshot save`, stored securely; test restores |
| **Separate hosts** | In large clusters, run etcd on dedicated, locked-down nodes |

### Encryption at rest

The API server encrypts resources before writing them to etcd:

```yaml
# /etc/kubernetes/enc/encryption-config.yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources:
  - secrets
  providers:
  - aescbc:                 # or kms (v2) with an external key service, which is preferred
      keys:
      - name: key1
        secret: <base64-encoded 32-byte key>
  - identity: {}            # fallback so existing unencrypted data can still be read
```

Enable it with `--encryption-provider-config` on the API server, then rewrite existing Secrets so they're stored encrypted:

```bash
kubectl get secrets -A -o json | kubectl replace -f -
```

More on etcd itself, with a hands-on HA cluster, in the [CKA folder](../03-CKA/README.md).
