# 10. Pod Security Standards and Admission

**Pod Security Standards (PSS)** and **Pod Security Admission (PSA)** work together to enforce security best practices at the pod level:

- **PSS** is the *building code*: three standard levels of pod hardening.
- **PSA** is the *building inspector*: a built-in admission controller that checks every new pod against the level chosen for its namespace, and rejects or flags pods that break it.

> **History:** PodSecurityPolicy (PSP) did this job before. It was deprecated in v1.21 and **removed in v1.25**. PSA has been stable since **v1.25** and is enabled by default. Exam questions may still mention PSP; know that it's gone and PSA replaced it.

## Admission Controllers in General

Admission controllers intercept requests to the API server **after** authentication and authorization, and **before** the object is stored in etcd.

| Type | What it does | Examples |
|---|---|---|
| **Mutating** | Changes the object, for example adding defaults | `ServiceAccount`, `DefaultStorageClass`, `LimitRanger` (defaults), mutating webhooks |
| **Validating** | Accepts or rejects the object | `PodSecurity`, `ResourceQuota`, `NodeRestriction`, validating webhooks, ValidatingAdmissionPolicy |

Mutating controllers run first, then validating ones.

## The Three Standards

| Level | Purpose | Key restrictions |
|---|---|---|
| **privileged** | Unrestricted; for trusted system workloads | None |
| **baseline** | Blocks known privilege escalations, while staying easy to adopt | No `privileged`, no `hostNetwork`/`hostPID`/`hostIPC`, no `hostPath` volumes, no host ports, only safe capabilities, no unconfined AppArmor or seccomp override |
| **restricted** | Current hardening best practice | Everything in baseline, **plus**: `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, capabilities `drop: ["ALL"]` (only `NET_BIND_SERVICE` may be added), seccomp `RuntimeDefault` or `Localhost`, limited volume types |

## The Three Modes

Each namespace can set a level for each mode:

| Mode | Effect on a violating pod |
|---|---|
| **enforce** | **Rejected** |
| **audit** | Allowed, but an annotation is added to the audit log event |
| **warn** | Allowed, but the user sees a warning |

## How PSA Evaluates a Pod

1. A user or controller sends a pod creation request to the API server.
2. The **PodSecurity** admission controller intercepts it.
3. It reads the pod's security-relevant fields: security contexts, host namespaces, volumes, capabilities, seccomp and AppArmor settings.
4. It compares them with the level set for the namespace.
5. **Compliant:** the pod is created. **Non-compliant:** rejected (enforce), annotated (audit) or warned about (warn).

> PSA checks pods created **by controllers** too. A Deployment is accepted, but its ReplicaSet fails to create violating pods; check `kubectl describe rs` for the reason. The `warn` mode helps here because it also warns on workload objects.

## Applying It: Namespace Labels

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: prod
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/audit: restricted
```

Or on an existing namespace:

```bash
kubectl label namespace dev \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/warn=restricted
```

> These are **labels**, not annotations. The `-version` label pins the rules to a Kubernetes version (for example `v1.30`) so upgrades don't suddenly tighten them.

### Try a level before enforcing it

```bash
kubectl label --dry-run=server --overwrite namespace prod \
  pod-security.kubernetes.io/enforce=restricted
# Warning: existing pods in namespace "prod" violate the new PodSecurity enforce level "restricted:latest"
# Warning: web-7d9f: allowPrivilegeEscalation != false, unrestricted capabilities, runAsNonRoot != true, seccompProfile
```

## A Pod That Passes `restricted`

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
  namespace: prod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: web
    image: nginxinc/nginx-unprivileged:1.27
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
```

## Cluster-Wide Defaults

To give every namespace a default, configure the admission plugin with an `AdmissionConfiguration` file passed to the API server with `--admission-control-config-file`:

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
- name: PodSecurity
  configuration:
    apiVersion: pod-security.admission.config.k8s.io/v1
    kind: PodSecurityConfiguration
    defaults:
      enforce: baseline
      enforce-version: latest
      warn: restricted
      warn-version: latest
    exemptions:
      namespaces: ["kube-system"]
```

## Going Beyond PSS

PSS covers pod fields only. For custom rules (allowed registries, required labels, resource limits), add a policy engine: **OPA Gatekeeper** ([CKS topic 16](../04-CKS/16.%20OPA%20Gatekeeper%20Policies.md)), **Kyverno**, or the built-in **ValidatingAdmissionPolicy** (CEL rules, stable since v1.30).

## Best Practices

- Label **every** namespace; start with `warn` and `audit`, then move to `enforce`.
- Use `baseline` as the minimum everywhere and `restricted` for application namespaces.
- Keep `privileged` for system namespaces only, and limit who can change namespace labels (RBAC on `namespaces` with `update`/`patch`).
- Audit regularly: kube-bench (CIS checks) and kube-hunter (attack simulation).
