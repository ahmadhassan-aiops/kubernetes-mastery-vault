# 04. Isolation Techniques

**Isolation and segmentation** keep workloads apart, so a problem in one (a breach, a bug, a resource hog) can't spread to the rest of the cluster. This is essential for **multi-tenancy**: many teams or applications sharing one cluster.

Why it matters:

- **Security boundaries:** a compromised application stays contained in its segment (a smaller "blast radius").
- **Multi-tenancy:** tenants can't interfere with each other's resources.
- **Resource management:** one workload can't starve the others.

## The Techniques

### 1. Namespaces

- **What:** a virtual division of cluster resources between users, teams or environments.
- **Why:** a scope for names, and the unit for RBAC, quotas, network policies and Pod Security.
- **Example:** run development, testing and production in separate namespaces to prevent accidental interactions.
- **Limit:** a namespace on its own is **not a security boundary**. Pods in different namespaces can still talk to each other and share nodes until you add the controls below.

### 2. Network Policies

- **What:** rules controlling traffic between pods and other endpoints.
- **Why:** only intended communication is allowed.
- **Example:** front-end pods may reach back-end pods; all other traffic is blocked.
- **Needs** a CNI plugin that enforces policies (Calico, Cilium). Hands-on: [CKS topic 02](../04-CKS/02.%20Network%20Policies%20and%20Protecting%20Node%20Metadata.md).

### 3. Pod Security Standards

- **What:** built-in rules for the security-sensitive parts of a pod spec, enforced per namespace by **Pod Security Admission** (the replacement for the removed PodSecurityPolicy).
- **Why:** blocks privileged pods, host namespaces, risky volume types and running as root.
- **Example:** enforce `restricted` so all pods run as non-root and can't use the host network. See [topic 10](10.%20Pod%20Security%20Standards%20and%20Admission.md).

### 4. Resource Quotas and Limits

- **What:** **ResourceQuotas** cap total consumption per namespace; **limits** cap each container.
- **Why:** prevents one tenant from consuming everything, which would be a denial of service for the others.
- **Example:** no namespace may use more than a set amount of CPU and memory.

### 5. Node Isolation

- **What:** scheduling rules that decide which nodes certain pods may run on.
- **Why:** sensitive workloads run on dedicated nodes with stricter controls, away from untrusted ones.
- **Example:** taint the sensitive nodes, and give only approved pods the matching toleration plus node affinity.

### 6. Sandboxed Runtimes

- **What:** container runtimes that add an extra isolation layer between the container and the host kernel: **gVisor** (a user-space kernel) or **Kata Containers** (a lightweight VM per pod), selected with a **RuntimeClass**.
- **Why:** untrusted or multi-tenant code can't attack the shared kernel directly.

### 7. Service Mesh

- **What:** a mesh such as **Istio** or **Linkerd** adds a proxy to every pod.
- **Why:** consistent policy enforcement, **mutual TLS (mTLS)** encryption and identity between services.
- **Example:** Istio automatically encrypts all service-to-service traffic and only allows calls that a policy permits.

## Isolation Checklist

**Namespaces**
- [ ] Separate namespaces per environment (dev, test, prod) and team
- [ ] RBAC limits access per namespace
- [ ] Namespace access reviewed regularly

**Network Policies**
- [ ] Default-deny policy in every namespace, then explicit allows
- [ ] Policies tested to confirm they block what they should
- [ ] Policies updated when the application architecture changes

**Pod Security**
- [ ] Pod Security Admission labels on every namespace (`baseline` at least, `restricted` where possible)
- [ ] Privileged containers blocked
- [ ] All pods meet the standard before reaching the cluster (checked in CI)

**Resource Quotas and Limits**
- [ ] A ResourceQuota per namespace
- [ ] CPU and memory requests and limits on every container (a LimitRange supplies defaults)
- [ ] Usage monitored, quotas adjusted as needed

**Node Isolation and Affinity**
- [ ] Taints on nodes reserved for sensitive workloads
- [ ] Affinity and anti-affinity rules for secure, resilient placement
- [ ] Node and pod placement reviewed regularly

**Service Mesh**
- [ ] A mesh chosen and installed where service-to-service security is needed
- [ ] mTLS enabled (strict mode)
- [ ] Mesh telemetry used to detect unusual communication

## Good Practice

- Apply **least privilege** through every technique.
- **Audit** the effectiveness of isolation regularly.
- **Train** everyone who deploys to Kubernetes on why and how these controls are used.
