What this tells us:

| Observation | Meaning |
|---|---|
| `Controlled By: Node/minikube`, `config.source: file` | etcd is a **static pod**, started by the kubelet from a manifest file |
| `--advertise-client-urls ...:2379` | Clients (the API server) connect on **2379** |
| `--listen-peer-urls ...:2380` | Peers would connect on **2380** |
| `--client-cert-auth=true` | Every client must present a certificate |
| `--data-dir=/var/lib/minikube/etcd` | The database lives on the node, mounted as a **hostPath** |
| Liveness, readiness and startup probes on `:2381` | etcd's health endpoints |

## Querying etcd with etcdctl

Because client certificate authentication is on, every `etcdctl` call needs the **CA, certificate and key** paths from the pod spec. `ETCDCTL_API=3` selects the v3 API.

### List every key

```bash
kubectl exec -n kube-system etcd-minikube -- \
sh -c "ETCDCTL_API=3 etcdctl \
  --endpoints=https://192.168.49.2:2379 \
  --cacert=/var/lib/minikube/certs/etcd/ca.crt \
  --cert=/var/lib/minikube/certs/etcd/server.crt \
  --key=/var/lib/minikube/certs/etcd/server.key \
  get / --prefix --keys-only"
```

### Write and read your own key

```console
[ahmad@client1 ~]$ kubectl exec -n kube-system etcd-minikube -- sh -c "ETCDCTL_API=3 etcdctl \
  --endpoints=https://192.168.49.2:2379 \
  --cacert=/var/lib/minikube/certs/etcd/ca.crt \
  --cert=/var/lib/minikube/certs/etcd/server.crt \
  --key=/var/lib/minikube/certs/etcd/server.key \
  put name ahmad"
OK

[ahmad@client1 ~]$ kubectl exec -n kube-system etcd-minikube -- sh -c "ETCDCTL_API=3 etcdctl \
  --endpoints=https://192.168.49.2:2379 \
  --cacert=/var/lib/minikube/certs/etcd/ca.crt \
  --cert=/var/lib/minikube/certs/etcd/server.crt \
  --key=/var/lib/minikube/certs/etcd/server.key \
  get name"
name
ahmad
```

`get` prints the **key** on one line and the **value** on the next.

> Writing your own keys is fine for learning, but **never edit `/registry` keys directly** on a real cluster; always go through the API server.
